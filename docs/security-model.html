Statoblast Core Security Assumptions

  1. Users are greedy

    Users are economically motivated and prefer outcomes that leave them with more value over otherwise-equivalent outcomes that leave them with less.

  2. A fork preserves enough system value

    The aggregate market value of assets in the resulting child universes remains large enough compared with the parent universe under the configured Statoblast securityMultiplier.

    Value prior universe ≤ ∑ universe∈Future universes Value universe securityMultiplier

    Fork value boundary. The configured Statoblast securityMultiplier sets the required relationship between parent and aggregate child value.

  3. Market capitalization approximates economic value

    REP market capitalization is a sufficiently accurate proxy for the discounted cash flow participants expect from the asset.

  4. Users value truthful universes

    Users prefer the universe or universes they judge truthful, so economic activity and durable asset value concentrate there.

    Value before fork ≈ Value truthful universe

    Value concentration. The universe users regard as truthful retains approximately the pre-fork system value.

  5. Operating costs are small

    Transaction fees and other operating costs are negligible relative to the financial value of the actions they protect.

  6. Participants can access timely information

    Users can reliably obtain enough information, soon enough, to decide which market outcome and child universe they consider truthful.

  7. Migration is practical

    Users, exchanges, interfaces, and other integrations are willing and able to migrate into the child universe they support.

  8. The system has enough independent users

    Enough non-colluding participants exist for the relevant activity. Prediction-market trading, for example, requires participants willing to take opposing views.

  9. Auctions convert assets efficiently

    A truth auction can sell some truthful-universe REP for ETH lost during a fork at an acceptably small cost.

  10. Participants can mobilize REP to raise an alarm

    Market participants can mobilize enough vault-backed REP through security-vault operators to fund an early competing Invalid, Yes, or No outcome deposit. That keeps the local outcome contest active long enough for better-capitalized participants to react and continue escalation. See Escalation Resolution.

  11. REP is sufficiently liquid

    Participants can acquire reasonable amounts of REP from the open market when reporting, disputing, or migration requires it.

  12. REP economic value exceeds open interest

    The system can maintain the strict backing relationship below; market capitalization is used as the observable proxy described in assumption A03. This is an ongoing assumption: the inequality must hold at every relevant time, comparing values for the same system scope and timestamp.

    OpenInterest < DCF REP

    Economic backing. REP discounted cash flow must remain strictly greater than open interest.

  13. Access to Statoblast is valuable

    Users value continued access to prediction markets through Statoblast at least as highly as the configured Statoblast securityMultiplier times the value secured by the system.

    Value Statoblast access ≥ securityMultiplier × Value secured

    Access-value boundary. Continued Statoblast access must justify the configured securityMultiplier applied to secured value.

  14. Ethereum remains censorship resistant

    Users can submit Ethereum transactions and obtain inclusion within the time required by the relevant protocol deadline.

  15. Honest reporters can access sufficient capital

    Honest reporters hold or can acquire enough REP for local escalation under the configured game rules. Price-oracle correction additionally requires scenario-dependent WETH and REP positions.

  16. Price-oracle reporting has an independent corrector

    The sponsor-funded coordinator reporting path and at least one correcting OpenOracle participant are economically independent and do not collude. The independent participant is willing and able to risk the WETH and REP required to replace an incorrect report when correction is profitable and can obtain transaction inclusion before settlement. The contracts do not guarantee that a profitable correction always exists.

OpenOracle Economic Boundary

External correction remains an assumption. A16 requires an independent participant to correct an incorrect report when doing so is profitable. Report sizing does not prove that executable venue liquidity, gas, timing, and inclusion make a correction profitable for every market state.

Report liquidity is a correction incentive, not collateral for the assets whose solvency checks consume the resulting price. The coordinator intentionally imposes no downstream-notional or cumulative cache-usage cap. One accepted price may support multiple otherwise-valid withdrawals, liquidations, allowance updates, or escalation deposits while it is fresh.

If monitoring, capital, or timely inclusion fails, the protocol places no onchain upper bound on loss based on the report position. For example, a report funded with a few WETH can still be consumed by operations whose combined external value is hundreds of ETH. That mismatch is expected: the claimed defense is profitable correction before settlement, not reimbursement after a false price is accepted.

Implementation and test evidence: OpenOraclePriceCoordinator.sol, priceOracleSecurity.test.ts (dynamic minimum sizing and repeated cached-price use), and the full integration threat model.

Truth-Auction Loss Boundary

Intentional loss-allocation rule. A truth auction is both a collateral-repair mechanism and a penalty for security capital that does not migrate into the child. The cap-implied underfundedThreshold is a bid-qualification threshold. It is not an execution-price floor.

When ordinary clearing reaches neither auction cap, bids at or above the qualifying tick are retained. If any ETH qualifies, those bidders collectively receive maxRepBeingSold for their actual retained ETH and share the complete unmigrated security-bond allowance. The common effective price is therefore underfundedWinningEth / maxRepBeingSold, which can be below the qualification threshold. Bids below the threshold refund. If no bid qualifies, all bids refund and no REP is sold.

The auction clearing design owns the qualification formula, tick rounding, worked examples, and per-bid allocation rules.

The child activates with the ETH actually routed during migration plus the ETH actually retained by the auction. It may remain undercollateralized, and open-interest holders are not guaranteed to be made whole. That shortfall is the intended consequence of insufficient demand: non-migrating security positions lose the auctioned economic value, while users of the affected child bear any remaining collateral impairment.

Implementation and test evidence: UniformPriceDualCapBatchAuction.sol, SecurityPoolForker.sol, SecurityPoolForkerVaultMigrationDelegate.sol, truthAuction.test.ts (the minimum-bid underfunded-winner test), and the full clearing design.

Review and Deployment Classification

The accepted assumption, design properties, and loss-allocation policy do not remove these paths from security review. They change the question from “does Solidity enforce an excluded property?” to “does the implementation conform, and is the external assumption credible for deployment?”

Review result Classification Required response
Code deviates from the sizing, qualification, allocation, refund, activation, or accounting behavior defined above. Implementation vulnerability, with severity based on impact. Fix the contracts and add a regression test.
Code conforms, but the review demonstrates that profitable correction or timely inclusion is not credible under launch parameters. Deployment-blocking economic risk. Change parameters, design, or liquidity and repeat executable market and inclusion testing before deployment.
Code conforms and the concern is only that report liquidity does not bound downstream notional. Documented residual risk, normally informational rather than a new vulnerability. Confirm the external-correction assumption and downstream exposure remain acceptable for the intended deployment.
Code conforms, but weak truth-auction demand may leave the child under-repaired. Documented truth-auction loss-allocation risk. Change the auction design or explicitly approve the quantified residual loss policy before deployment.

Launch monitoring should track OpenOracle report visibility, correction profit after current gas and fees, practical inclusion latency, truth-auction participation, and the collateral deficit remaining after each auction. Monitoring detects oracle-assumption or auction-demand deterioration; it does not add an onchain guarantee or an emergency control.
