Stage an oracle-backed operation

Follow the procedure below when a liquidation, withdrawal, or coverage change needs a fresh REP/ETH price.

Preflight

Observation Consequence
isPriceValid() == true No new report bounty or initial report position; the operation may execute immediately.
Stale price and pendingReportId() == 0 The caller opens and funds a report.
pendingReportId() != 0 and caller is pendingReportSponsor() The operation may join the pending batch.
pendingReportId() != 0 and caller is not the sponsor Do not submit; the caller restriction will fail.
Pending batch is full The operation remains active and requires later manual execution.

Also read lastPrice(), lastSettlementTimestamp(), getRequestPriceCostAttoEth(), getSettlementCallbackGasLimit(), the target vault state, and the current pool lifecycle. Record the release, chain, block, coordinator, target, caller, and operation kind before submitting.

  • validForSeconds must be in 1..MAX_OPERATION_VALID_FOR_SECONDS; the operation expires after queuedAt + settlementTime + validForSeconds.
  • Liquidation and withdrawal amounts must be positive. A coverage update may be zero, but it must still satisfy its pool guard.
  • A liquidation targets another vault. A withdrawal or coverage update targets the caller's own vault. The local escalation must not already be resolved.
  • When a report is pending, only pendingReportSponsor() may queue another operation. The callback auto-executes at most MAX_PENDING_SETTLEMENT_OPERATIONS() operations; later active operations require manual execution.

Worked call

Record the target, operation amount, current price validity, request cost, minimum WETH report amount, proposed price, and selected initial WETH from the same block. Do not copy values from this page: the coordinator derives the required WETH and REP amounts from deployment parameters, current base fee, and the requested operation.

requestPriceIfNeededAndStageOperation(
  SetCoverageCommitment, targetVault, 5 ETH, validForSeconds,
  2 REP/ETH, 0.5 WETH
){ value: 0.003 ETH }

Verify StagedOperationQueued, StagedOperationDisputeStakedRepSnapshotted, and PriceRequested when the stale branch opens a report.

Stage the operation

Call requestPriceIfNeededAndStageOperation(operation, targetVault, operationAmountAttoRepOrAttoEth, validForSeconds, proposedRepPerEthPrice, requestedInitialAttoWeth) with msg.value covering getRequestPriceCostAttoEth() only when the call opens a new report. The coordinator pulls the selected initial WETH and derived REP position from the sponsor with ERC-20 transferFrom; approve those WETH and REP amounts to the coordinator separately. Read minimumToken1ReportAttoEth() and the current base fee before choosing requestedInitialAttoWeth; the coordinator selects the greater required WETH amount and derives the REP side with ceiling division.

Branch Caller and value Expected result
Fresh cache Valid operation caller; no oracle bounty. StagedOperationQueued, then ExecutedStagedOperation if the pool guard succeeds. A failed downstream guard consumes the operation with success == false.
First stale request Any valid operation caller; request bounty plus initial report position. StagedOperationQueued, StagedOperationDisputeStakedRepSnapshotted, and PriceRequested. The caller becomes pendingReportSponsor.
Pending report Only the existing sponsor; no additional join bounty. The operation joins the bounded pending list. If the list is full, it remains active outside the callback batch and must be executed manually after a fresh price.
Rejected report After callback rejection, re-read price and pending state before retrying. PriceReportRejected; queued operations remain subject to expiry and require a replacement request or manual execution when eligible.

Verify and hand off recovery

Require StagedOperationQueued, StagedOperationDisputeStakedRepSnapshotted, PriceRequested, or ExecutedStagedOperation according to the branch. When the report is rejected, the callback fails, or an operation remains outside the callback batch, continue with Recover an oracle-backed operation.

Completion checklist

  • Operation ID and branch event recorded.
  • Cached price, pending IDs, and operation activity reconciled.
  • Target state, balances, and accounting checkpoint match the receipt.
  • Failed or consumed operations are not replayed without a fresh preflight.
