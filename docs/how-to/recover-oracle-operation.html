Recover an oracle-backed operation

Choose the recovery branch from observable coordinator state. A low-level callback failure, price rejection, consumed staged operation, and queued overflow operation have different calls and events.

Choose the branch

Observed state Action Completion evidence
Settled OpenOracle report, coordinator still has a pending ID Call recoverSettledPendingReport(), then inspect the pending list and active operation slots again. PendingReportRecovered; the current slot is consumed, while remaining queued operations need a later valid-price path.
PriceReportRejected Call requestPrice(proposedRepPerEthPrice, requestedInitialAttoWeth) only when isPriceValid() is false. PriceRequested or a valid cached price.
Staged operation reports failure Re-read and stage a new operation with current parameters. New operation ID and branch event.
Active operation outside the callback batch Call executeStagedOperation(operationId) while price and timeout remain valid. ExecutedStagedOperation and changed target state.

Record authoritative state

Record the coordinator, operation identifier, requester, operation kind, parameters, pending report identifier, pending settlement slot, isPriceValid(), expiry, and the OpenOracle report's settlement timestamp from one block. Do not infer the branch from the settlement transaction alone.

Recover a low-level callback failure

If OpenOracle shows the report as settled but the coordinator still holds that pending report identifier, the callback did not complete at the coordinator. Anyone may call recoverSettledPendingReport(). It clears the pending report and settlement base-fee cap in one call. When pendingOperationSlotId identifies a live staged operation, recovery deactivates that operation, removes it from the active and pending collections, emits PendingOperationRecoveryConsumed, and advances the slot to the next remaining operation. Other queued operations remain active. Recovery does not emit ExecutedStagedOperation, accept a price, or execute an operation.

Replace a rejected price report

If the callback entered the coordinator and emitted PriceReportRejected, the pending report is already cleared and queued staged operations remain active. Fund a replacement with requestPrice(proposedRepPerEthPrice, requestedInitialAttoWeth); after a valid settlement, the bounded pending batch can execute. Do not call recoverSettledPendingReport() because no pending report remains.

Handle the operation result

  • If ExecutedStagedOperation reports failure, that operation was consumed. Revalidate current pool and vault state, then stage a new operation with new parameters if the action remains valid.
  • For a new coverage, withdrawal, or liquidation operation, stage it with requestPriceIfNeededAndStageOperation(operation, targetVault, operationAmountAttoRepOrAttoEth, validForSeconds, proposedRepPerEthPrice, requestedInitialAttoWeth); stale-price branches also require the coordinator's ETH bounty and WETH/REP approvals.
  • If the operation was outside the bounded callback batch and remains active while the cached price is fresh, anyone may call executeStagedOperation(operationId).
  • If an active overflow operation outlives the price or its timeout, obtain a later valid price or stop; there is no generic retry, clear, completion, or supersede entrypoint.

Execute and reconcile

Preview the branch-specific call against the current block, submit it with an inclusion margin, and reconcile CoordinatorStateCheckpoint, the branch event, staged-operation activity, cached price state, pool accounting, and token balances. Recovery is permissionless where the ABI permits it, but a consumed failure is evidence, not a retryable instance.

Prevent retry loops

Indexers should key recovery attempts by operation and resulting state, not settlement transaction alone. Alert on repeated rejection without a state change. The canonical branch semantics are in callback rejection and recovery; the exact calls and events are in the coordinator reference.
