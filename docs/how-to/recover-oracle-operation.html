Recover an oracle-assisted operation

Choose the recovery branch from observable coordinator state. A low-level OpenOracle callback failure, a coordinator price rejection, a failed staged operation, and a queued overflow operation have different calls and events.

Record authoritative state

Record the coordinator, operation identifier, requester, operation kind, parameters, pending report identifier, pending settlement slot, price-validity state, expiry, and the OpenOracle report's settlement timestamp. Do not infer the branch from the settlement transaction alone.

Recover a low-level callback failure

If OpenOracle shows the report as settled but the coordinator still holds that pending report identifier, the callback did not complete at the coordinator. Anyone may call recoverSettledPendingReport(). It clears the pending report and settlement base-fee cap. When pendingOperationSlotId identifies a live staged operation, recovery deactivates that operation, removes it from the active and pending collections, emits PendingOperationRecoveryConsumed, and advances the slot to the next remaining operation. Stage that consumed operation again with current parameters if it is still valid. Other queued operations remain active and need a later valid-price path. Recovery does not emit ExecutedStagedOperation, accept a price, or execute an operation.

Replace a rejected price report

If the callback entered the coordinator and emitted PriceReportRejected, the pending report is already cleared and queued staged operations remain active. Fund a replacement with requestPrice(proposedRepPerEthPrice, requestedInitialWethAttoEth); after a valid settlement, the bounded pending batch can execute. Do not call recoverSettledPendingReport() because no pending report remains.

Handle the operation result

  • If ExecutedStagedOperation reports failure, that operation was consumed. Revalidate current pool and vault state, then stage a new operation with new parameters if the action remains valid.
  • If the operation was outside the bounded callback batch and remains active while the cached price is fresh, anyone may call executeStagedOperation(operationId).
  • If an active overflow operation outlives the price or its timeout, obtain a later valid price or stop; there is no generic retry, clear, completion, or supersede entrypoint.

Execute and reconcile

Preview the branch-specific call against the current block, submit it with an inclusion margin, and reconcile CoordinatorStateCheckpoint, the branch event, staged-operation activity, cached price state, pool accounting, and token balances. A consumed failure is evidence, not a retryable instance.

Prevent retry loops

Indexers should key recovery attempts by operation and resulting state, not settlement transaction alone. Alert on repeated rejection without a state change. The canonical branch semantics are in callback rejection and recovery; the exact calls and events are in the coordinator reference.
