Build a reorg-safe event indexer

Build a replayable reducer that reconstructs Zoltar and Statoblast protocol state from canonical logs and recovers deterministically from chain reorganizations.

Prerequisites and acceptance result

Choose one chain and reviewed deployment manifest. Your indexer needs an RPC with block and log pagination, a durable database, and the schemas in the event-stream reference. The task is complete when a clean replay and a replay after a simulated reorg produce the same final state hash.

Anchor the schema

Record chain ID, schema version, contract-address set, and the successful ZoltarQuestionData deployment receipt. Use that receipt's block as the inclusive protocol start. Track Genesis REP from its own earlier deployment anchor.

Discover emitters before reduction

Pre-scan factory and pool relationship events for pool, share-token, auction, coordinator, and escalation-game addresses. Constructor and setup logs can occur before the relationship event later in the same transaction, so a forward-only allowlist loses canonical state.

Reduce canonical logs

  1. Sort by block number, transaction index, and log index.
  2. Handle removed logs before deduplication; then use chain ID, block hash, transaction hash, and log index as the idempotency identity.
  3. Apply the canonical reducers and replace resulting-value fields rather than accumulating them.
  4. Keep OpenOracle packed-log reconstruction in its separately defined state machine.
for block in canonicalBlocks(afterCheckpoint):
  persistBlock(block)
  branchReplayed = false
  for log in sortLogs(block.logs):
    if log.removed:
      rollbackToCheckpointBefore(log.blockNumber)
      replayCanonicalReplacementBranch(log.blockNumber)
      branchReplayed = true
      break
    if log.identityAlreadyStored(): continue
    reducer.apply(log, state)
  if not branchReplayed:
    checkpoint(block.number, block.hash, hash(state))

Checkpoint and verify

Persist reducer state with the canonical block hash and reducer version. Use the deployment's stated confirmation or finality policy before publishing a checkpoint. At each checkpoint, compare reconstructed state with documented storage getters. A mismatch is an audit signal; do not silently patch event-derived state.

Handle reorganizations

Detect a reorganization when the next block's parentHash does not equal the stored canonical head hash; removed-log notifications are an additional signal, not the sole detection mechanism. Discard affected events, restore the checkpoint's versioned state snapshot before the replacement, and replay the new branch. Alternatively replay all retained canonical logs from the schema anchor. Never merge events from deployments or schema segments by event name alone. Use the event-stream reference for exact schemas and reducers.

Acceptance tests

  • Deliver the same log twice: entity state and state hash remain unchanged.
  • Deliver a stored log followed by its removed form: rollback removes its effect, and replaying the replacement branch produces the expected state hash.
  • Deliver two logs from one transaction: transaction index and log index preserve their order.
  • Discover a new pool and its emitter in the same block: all later logs reduce successfully.
  • Replace a checkpointed branch: discard the affected branch checkpoint, replay the canonical replacement branch, and checkpoint only its replacement block hash and state.
  • Persist the expected final state hash with the fixture and reducer version.
