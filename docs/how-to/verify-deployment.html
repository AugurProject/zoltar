Verify a protocol deployment

This guide combines one automated manifest-freshness check with manual runtime verification. The repository does not currently provide a complete verifier for bytecode, wiring, permissions, and operational readiness; do not describe this procedure as an automated verifier.

Select the manifest

Start from the reviewed release manifest for the intended chain. Do not discover a canonical address from an untrusted interface, RPC response, or transaction history alone. Confirm chain ID and genesis block before comparing addresses.

Automated: validate manifest freshness

The repository command checks both the Mainnet and Sepolia deployment manifests; its output identifies which manifest is stale. Select the intended chain ID before comparing addresses.

bun run check:mainnet-deployment:current

Expected result: zero exit status and a report naming the current manifest and validation source. A non-zero exit status means at least one manifest is not fresh; preserve the output rather than proceeding.

This is the only automated check supplied by this guide. Preserve its output, the selected manifest hash, chain ID, and verification block before continuing with the manual checks.

Manual: verify runtime code

  1. Fetch runtime bytecode independently from at least two RPC providers.
  2. Hash it and compare it with the reviewed artifact.
  3. Reject missing code, proxy indirection not named by the design, or a mismatch at any required address.
  4. Verify external Genesis REP and WETH implementations and behavior separately.

Record one result for each address: eth_getCode present, runtime hash equal, and provider responses equal. A code-present result alone is not a hash match.

Manual: normalize and hash code

Compare deployed runtime code with the runtime artifact, not creation bytecode. Record whether metadata, linked-library addresses, constructor immutables, or proxy indirection are part of the reviewed build. Never strip bytes ad hoc to make a hash match; document the exact normalization rule and artifact source.

Manual: verify contract wiring and permissions

Read constructor-derived and immutable relationships from the deployed contracts. Confirm the Zoltar registry, question data, factories, root universe, REP token, WETH, pool components, coordinator, auction, and escalation modules point to the addresses in the release evidence. Mark permissions and lifecycle readiness separately from wiring.

Manual: read deployment progress

Use DeploymentStatusOracle.getDeploymentMask() only to determine which configured step addresses contain runtime bytecode. A full mask is not proof of correct initialization or wiring. Interpret the bits using the deployment status reference.

Publish the manual report

Record chain ID, block number, manifest hash, address set, bytecode hashes, wiring results, RPC sources, and verifier identity. Separate code present, code hash correct, wiring correct, permissions correct, and operationally ready. If any result is unknown, do not label the deployment canonical.
