How-to guide

Monitor security assumptions

Check that the economic and liveness assumptions behind a deadline-bearing or price-sensitive action still hold before you take it, and keep checking until its last deadline. The contracts cannot tell you when such an assumption has stopped holding.

Check an action's assumptions

  1. List the assumptions the action depends on. The security model lists which assumptions protect which mechanism.
  2. Find the rows for those assumptions in the table below.
  3. Record the lineage, ledger, block number and hash for the decision. Use one block for current state. For A07, record the pre-fork parent and repair-time child snapshots separately. Compare values in one collateral unit.
  4. Label each result observed, estimated or unknown. If a read fails or the block hash changes, retry the complete snapshot while time permits. Use canonical block-hash reads where supported and recheck the hash for number-only reads. Discard a stale simulation. If evidence is still missing, apply the row’s response.
  5. Repeat the reads on the row's cadence until the action's last deadline has passed.

Most on-chain reads are also indexed by augurScan under /operations/… (see the augurScan README). The liquidator and OpenOracle arbitrager bots in bots/ show live security pool, vault, and report state in their dashboards.

Terms used in the table

Corrector
An account that disputes an incorrect OpenOracle report; see A17.
Callback-recovery candidate
A report OpenOracle has settled but the shared feed has yet to process; see settlement recovery.

Reads, cadence, and response for each assumption

Assumptions What to read Review cadence Response when the boundary is weak or unknown
Executor incentives and participation — A01, A02, A03, A06
  • Name the next caller, its benefit, capital costs and ETH for gas. A takeover credits ledger principal and also needs receiver consent. Use the liquidator dashboard to check blockers.
  • Check whether a funded caller will settle, including third-party settlement settings on a bot. For a contest, identify funded opposing support.
  • Use augurScan activity in /operations/reports, /operations/escalations and /operations/auctions to identify participants. Establish independent control separately.
  • For a settled report whose callback failed or was deferred, follow settlement recovery.
 Continuously for deadline-bearing flows; before launch and after parameter or gas-regime changes Fund or arrange independent executors, reduce exposed value, or disclose that the affected transition may stall
Fork lineage value and migration readiness — A05, A07, A09, A11
  • Fork start: Zoltar getForkTime(universeId)
  • Check native REP migration, each underwriter’s branch-choice deadline and each share holder’s ability to call migration into the active branch. Track the branches actually supported in /operations/forks.
  • Value parent backing at the pre-fork block and child backing at repair. Record both inventories and prices, and the portion of child REP available for sale.
  • For A05, name the participants choosing a branch, the access they lose, their next-best alternative and the secured exposure. Estimate a range. Mark deterrence unknown if that range crosses the hurdle.
 Before a fork-security claim and throughout migration and coordination windows Do not claim fork deterrence, practical migration, or value concentration; narrow supported lineage and exposure
REP value and liquidity versus secured exposure — A08, A13, A14
  • Theoretical REP supply: Zoltar getUniverseTheoreticalSupplyAttoRep(universeId)
  • Read question settlementCollateralAttoEth() with lastSettlementSecurityPoolTime(), its checkpoint. Define the exposure being valued. Pool oracle exposure and system-wide open interest can differ. Avoid counting the same REP backing independently for several ledgers.
  • REP deposited as underwriting capital: security pool capitalLedger(universeId), then the rep value from that ledger's totals()
  • For a valid nonzero lastPrice, raw collateral units = raw REP units × 1018 ÷ lastPrice. Apply the collateral decimals for display. Record the observation time and priceValidUntil. See the six-decimal example.
  • For any required trade, record the pair, direction, size and latest usable time. Quote at that size and account for inventory already held.
  • Security pool and vault risk: augurScan /operations/risk
  • Estimate discounted fee income off-chain. Record the supply and price basis of any market-cap proxy. If plausible valuations straddle the exposure, mark economic coverage unknown.
 At launch, continuously while open interest exists, and after material price, supply, liquidity, or exposure changes Cap or stop new exposure in clients and disclosures; do not describe REP backing as economically sufficient
Outcome evidence and escalation funding — A04, A10
  • Read getEscalationGameEndDate(), the last open second of the scheduled game. Project the new median and deadline after a change of leader. Check whether responders have time to deliver REP.
  • Required support, which closes the game once it exceeds binding capital while one outcome strictly leads: totalCostAttoRep()
  • Outcome funding: getOutcomeBalancesAttoRep() and getBindingCapitalAttoRep(), or augurScan /operations/escalations
  • Count wallet REP available for deposit. Add only principal the owner can withdraw and deliver before the cutoff.
  • Identify the resolution source and expected publication time. Allow time to interpret it, mobilize REP and obtain inclusion.
 From question creation through local resolution and any fork window Mark the market or action impaired, surface the deadline, and avoid asserting that honest local correction remains fundable
Collateral Repair Auction demand — A12
  • Collateral Repair Auction bids: auction engine(), then engine bidCount(), bids(index), and previewFinalization(maximumFilledLots, floorAttoRepPerLot), or augurScan /operations/auctions
  • Check that the auction opened with a fresh funded quote and at least one day for bidding. Closing needs a funded quote covering both pool collateral exposure and auction REP inventory, observed in the final day at or before close, and no fork at or before close. If ineligible, project zero proceeds even with funded bids.
  • For an eligible close, preview funded lots at the closing REP floor using available saleable inventory and the target lot cap. Collateral credited is the lesser of the shortfall and filled lots × collateral per lot. Estimate bidder costs and market depth separately.
 Before and during every repair auction Disclose likely incomplete repair and plan operation of the child at only migrated collateral plus collateral raised by the auction
Transaction inclusion and Ethereum execution — A16, A26
  • Base and priority fees: RPC eth_feeHistory
  • Estimate gas units for the actual call, compare transaction and block gas limits, then price the units. Estimate branch preparation and share migration as separate calls.
  • Reorg history: augurScan /operations/integrity
  • Escalation deadline: getEscalationGameEndDate()
  • Collateral Repair Auction close: auction closesAt()
  • Branch-choice cutoff: Zoltar getForkChoiceDeadline(universeId), eight weeks after the fork
  • For a shared-feed report at time t, disputes open at t + disputeDelay and close strictly before t + settlementTime. Use the deployed values.
  • Take the last eligible second (the scheduled deadline for escalation) and subtract expected inclusion delay to estimate the latest submission time. Subtract the current time for remaining slack. Fee history alone cannot establish inclusion.
 Continuously while a deadline or mandatory transition is live Raise transaction fees where rational, use independent submission paths, and disclose missed-deadline or stranded-transition risk
REP/collateral price correction — A17, A18, A19
  • Read PriceRequested events from the shared feed returned by SecurityPool.priceFeed(universeId), including a prepared branch with no question ledger yet, starting at feed deployment. For each report ID, read the feed’s reportOutcome(reportId). For a requested ID, 1 means accepted, 2 means rejected, and 0 needs follow-up.
  • For each unresolved ID, check OpenOracle storedGame(reportId) and follow settlement recovery if already settled. pendingReportId identifies only the latest candidate and can be zero while older candidates remain unresolved. For the active price, check the feed epoch and expiry. Acceptance at the same eligibility timestamp need not replace the cached price.
  • For each candidate, verify an executing signer on this network, universe and collateral, its approvals and its remaining position capacity. The reference bot can run in dry-run mode and defaults to one open position.
  • Creation-time floor: security pool minimumReportCollateral and the selected collateral token’s units and current ETH value
  • Correction economics: compare obtainable correction gains with OpenOracle fees, current ETH gas costs including approvals and recovery, price impact, and capital lockup under A18; do not compare the whole stake with gas alone
  • Net concurrent commitments against each corrector’s REP, collateral and gas funds. Check an independent reference venue at the intended size. Compare the same actor’s payoff from correcting and waiting, including any shared incentives or side payments that can be established.
 Continuously while a report is pending or a cached price can authorize operations Do not add exposure when correction is uneconomic; disclose that a wrong report can settle despite passing the funding checks. The floor is immutable: a higher minimum requires a new security pool.
Token behavior and recipient compatibility — A21, A22
  • Sepolia genesis REP code: keccak-256 of eth_getCode against reputationToken in EXPECTED_SEPOLIA_DEPLOYMENT_RUNTIME_CODE_HASHES (ui/zoltarShared/ts/protocol/deployment.ts)
  • Sepolia WETH code: the same against sepoliaPublished.weth.runtimeCodeHash in scripts/artifacts/uniswap-deployment.json
  • Mainnet genesis REP (Augur V2 REP Yes and REP No fork child tokens) and WETH code: an externally sourced reference hash (no repository pin)
  • Before the first genesis fork, monitor the external token’s gross getTotalTheoreticalSupply() separately from Zoltar’s net getUniverseTheoreticalSupplyAttoRep(0). Compare the gross value with the pre-fork supply bounds. For Sepolia, also compare it with shared/zoltar/ts/deployment/sepoliaRepAllocations.ts
  • From a disposable sender, simulate a withdrawal to check WETH redemption. Exercise the intended recipient’s native-ETH receive path or ERC-1155 callback for the actual delivery.
 Supply: continuously until the first genesis fork, and before genesis fork or burn actions. Token and recipient checks: at deployment verification and before first use of a new recipient or integration Reject the deployment or incompatible recipient; do not rely on redirected recovery
Deployments, clients, data, and keys — A20, A23, A24, A27, A28
  • Select the intended chain and Yes or No genesis release. Compare its manifest and wiring with the selected deployment. Check manifest freshness with bun run check:mainnet-deployment:current.
  • Explorer source verification: bun run verify:contracts -- --chain-id=<chain ID>
  • If the status oracle has no code, its mask is unavailable. Set bits indicate code presence only. Read getDeploymentMask()
  • Runtime hashes: release checklist
  • For inherited claims, record the indexer coverage start and snapshot block. Reconstruct the outcome snapshot root from canonical history and check membership. Include the nullifier path for standalone games.
  • Check the signer inventory and on-chain approvals for the owner, spender or operator, asset and chain. Inspect typed-data domains and nonces before signing.
 At release, on every environment or account change, and continuously for indexers Stop signing or operating, reject an unverifiable deployment, revoke compromised authority where possible, and re-establish canonical state from independent sources
Question selection — A15
  • Read the immutable title, description, dates and outcome labels from QuestionCreated. Compare the full terms with the intended question, or recompute its ID with getQuestionId.
  • Evidence plan and security pool relevance: off-chain review
 Before security pool selection Reject or warn on the selection; do not represent an admitted question as relevant or resolvable
Immutable parameters — A25
  • Deployed configuration: manifest protocolConfig
  • Fork and non-decision thresholds: Zoltar getForkThresholdAttoRep(universeId) and getNonDecisionThresholdAttoRep(universeId)
  • Oracle costs: shared feed getRequestPriceCostAttoEth() and getSettlementCallbackGasLimit()
  • Compare the fork threshold with minted child totalSupply(), then with REP willing holders can mobilize. A 50 REP threshold with 40 REP minted requires further migration before a fork is reachable.
 Before deployment and after any change in external gas or market conditions used by the model If migration is insufficient, disclose that the backstop is presently unreachable and recheck after migration. An unsuitable immutable configuration requires another deployment.
