Advance an escalation game

Move one escalation game from an active round to local settlement or fork continuation, with exact state checks at every transition.

Identify the game

Verify the pool, question, universe, active game address, round, tentative answer, deposit target, deadline, and whether the game is ordinary or a child continuation. Read systemState(), escalationGame(), and the game state from the deployed interface in the contract reference. Snapshot the block before calculating a deposit.

Prepare a deposit

Choose an eligible outcome and calculate the accepted REP amount from current state. Read securityVaults(msg.sender), getPoolAccountingSnapshot(), priceOracleManagerAndOperatorQueuer().isPriceValid(), and the game's round/deadline. The pool entrypoint is depositToEscalationGame(outcome, maximumDepositAttoRep); it escrows the caller vault's pool-held REP backing, not a wallet transfer, so no REP approval is required. Coverage-bearing pools require a fresh price and post-deposit coverage checks must pass.

Advance the round

Submit the deposit and require the DepositToEscalationGame event, updated side/round, and deadline in the receipt. The game reaches a local result through its own time and state rules; the pool's claim action is withdrawFromEscalationGame(outcome, depositIndexes), while an own fork uses forkZoltarWithOwnEscalationGame(securityPool). If a transaction reverts, inspect the round again because another participant may have advanced it. Record the claim and independent evidence for the underlying answer.

Settle or enter fork handling

If the game selects a local winner, settle it and verify claim accounting before withdrawal. If it reaches non-decision, activate the pool fork path and verify the Zoltar fork relationship. Do not treat a paused child continuation as an ordinary unsettled parent game.

Settle a locally resolved game

Confirm the game has a settled local outcome and is not awaiting a fork continuation. Call withdrawFromEscalationGame(outcome, depositIndexes) for one vault's deposits, then verify the withdrawal event, claim balances, and pool state. A transaction that only advances a timer is not settlement. For an own-fork continuation, the forker path is forkZoltarWithOwnEscalationGame(pool) rather than local withdrawal.

Continue in a child universe

For a forked pool, verify the child pool, parent snapshot, carry proof, and awaitingForkContinuation(). Materialize the required child state, follow truth-auction repair, and finalize any required auction. The configured SecurityPoolForker applies a haircut only when purchased REP removes a positive escalation allocation, while the game is paused. Incomplete aggregate backing reverts finalization; reconcile the missing backing and retry.

When the child is operational and still awaiting continuation, call permissionless resumeForkedEscalationGame(). Reconcile ForkContinuationResumed and the resulting game state. See the proof reference and architecture explanation.

Common failures and safe retry

Expired deadline, insufficient vault-backed REP, stale price for a coverage-bearing pool, post-deposit coverage failure, wrong outcome, already-advanced round, and child-not-operational are state errors: inspect and recalculate. A mined successful deposit is not safe to replay just because the UI did not refresh; use the receipt and event identity first.
