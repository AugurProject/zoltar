Liquidate an unsafe vault

Preview and execute one bounded liquidation using current pool accounting and the correct fresh-price path.

Verify the target

Read systemState(), getPoolAccountingSnapshot(), securityVaults(targetVault), getTotalPoolHeldAttoRep(), and the coordinator's pending-operation and price-validity state. Calculate the funded coverage commitment, REP award, backing units transferred, target residual/bad debt, and liquidator post-transaction health from the same block. Do not depend on a cached UI label.

Preview the call

Record requestedCommitmentTransferAttoEth, snapshotTargetBackingUnits, snapshotTargetCoverageCommitmentAttoEth, snapshotTotalPoolHeldAttoRep, and snapshotTotalRepBackingUnits from the same read. The coordinator invalidates a queued liquidation when the target backing units or target coverage commitment changes. The two pool-total snapshots are queue-time inputs forwarded to the downstream call; the pool recomputes live transfer amounts and does not use those totals as stale guards. A maximum request may leave residual coverage as bad debt; it does not create external collateral.

Prepare the liquidator

Use a distinct liquidator vault that remains non-liquidatable after accepting the transferred coverage commitment and award. The liquidator does not supply REP or ETH liquidation principal: the complete bonus-bearing award comes from the target's pool-held vault REP backing. A maximum request records any untransferred residual coverage commitment as bad debt; it does not draw an external backstop payment.

Stage on the correct price path

  1. Preview the transferable coverage commitment, complete target-funded pool-held vault REP backing award, and any residual bad debt from a maximum request.
  2. Call requestPriceIfNeededAndStageOperation(Liquidation, targetVault, requestedCommitmentTransferAttoEth, validForSeconds, proposedRepPerEthPrice, requestedInitialAttoWeth) from the liquidator vault with msg.value covering any coordinator bounty or queued-operation cost.
  3. If the cached REP/ETH price is fresh, the staged operation executes immediately and no report is created.
  4. If the price is stale, the requester sponsors the OpenOracle bounty and initial position; track the report and correction window through settlement.
  5. Re-evaluate target and liquidator state before any later execution.

A fresh price can execute immediately. A first stale operation opens and funds the report; an operation behind an existing pending report is submitted by its sponsor without a second report bounty. After a rejected report, call requestPrice(...) separately to refresh the queued work. A successful later execution emits ExecutedStagedOperation and calls the pool's downstream performLiquidation(...).

Execute and check the result

Verify the coordinator's execution result on either the immediate fresh-price path or after a valid report settles. Confirm the target's pool-held vault REP backing funded the complete award, the transferred coverage commitment and REP backing units reached the liquidator, a maximum request recorded only the untransferred residual as bad debt, and pool conservation properties still hold. A successful receipt must include VaultLiquidated when coverage moves, plus the relevant accounting checkpoints. A failed callback is not a successful liquidation.

Expected result and events

Require a successful coordinator receipt and a resulting PoolAccountingCheckpoint and VaultAccountingCheckpoint. The target's coverage and funded REP award move according to the preview; accrued fees and claims remain with the original vault. If the receipt contains a price rejection or callback failure, treat the liquidation as unexecuted and follow recovery rather than retrying identical parameters.

Partial versus maximum requests

For a partial request, determine whether the remaining target position is healthy. If it remains liquidatable, calculate the next bounded liquidation from the new state rather than reusing the previous request. For a maximum request, reconcile transferred commitment, funded award, and residual bad debt separately. Strict health comparisons and rounding direction are explained in Liquidation economics.

Recover or repeat

If execution conditions changed, use the staged-operation recovery path. If the target remains unsafe, calculate a new bounded chunk from current state; do not replay stale parameters. The liquidation explanation owns the economic rationale and formulas.

Completion checklist

  • Receipt is final and emitted events match the preview.
  • Target, liquidator, pool accounting, and token balances reconcile.
  • No stale pending operation remains; otherwise record its operation ID and branch to recovery.
