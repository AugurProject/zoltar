How-to guide

Launch a protocol release

Follow this guide before tagging a release of Zoltar, the fork oracle, and Statoblast, the prediction-market layer built on it (see the system overview). It lists the checks that must pass before the tag and, for Sepolia and deterministic testnets, the genesis REP review that determines every deterministic address there. Mainnet uses the existing REPv2 token and deploys no genesis REP.

Know what a release cannot do

The contracts are immutable: no operator can pause, upgrade, roll back, or rescue them after deployment, so a release publishes verifiable provenance instead (commit and tag, deterministic addresses, CI and QA results, production UI artifact hash, known limitations) and never describes a UI deployment as an emergency control. See EG05.

Run the release checklist

  1. From a fresh dependency install (bun install --frozen-lockfile), run bun run check:mainnet-deployment:generated. It fails when either generated deployment manifest is stale. If so, regenerate both manifests with bun ./tooling/contracts/check-mainnet-deployment.mts --write, which only rewrites mainnet-deployment-addresses.json and sepolia-deployment-addresses.json; review the diff, then rerun the check.
  2. Run bun run ui:build:prod. It repeats the manifest check, so it fails if a manifest is still stale.
  3. Confirm the build used the pinned compiler configuration in solidity/ts/compile.ts, the exact tool versions in solidity/package.json, and the imported OpenOracle profile in UPSTREAM.md.
  4. Review the pinned runtime-code hashes: the EXPECTED_*_RUNTIME_CODE_HASHES maps in ui/zoltarShared/ts/protocol/deployment.ts and ui/statoblastShared/ts/protocol/deployment.ts. bun ./tooling/testing/bun-test.mts --preload ./bun-test-setup-ui.ts ui/zoltar/ts/tests/protocol/deployment.test.ts ui/statoblast/ts/tests/protocol/deployment.test.ts confirms that a clean local build still matches the pinned hashes of the directly compiled steps (the deployment status oracle, Multicall3, ZoltarQuestionData, and five Statoblast artifacts); it does not cover the other pinned contracts. On Sepolia, rerunning bun run deploy:testnet checks the runtime code of every installed contract against its pinned hash; it is not read-only, because it needs PRIVATE_KEY, deploys any missing step, and then runs explorer verification. For any other deployed address, compare the keccak-256 hash of its eth_getCode result with the pinned hash by hand before marking the release canonical, and publish the reviewed hashes with the release.
  5. Push the final tag only after the CI gate succeeds on the same commit. The tag must match v<number> (for example v12); the Version deploy workflow rejects any other form. That workflow reruns CI, builds the InterPlanetary File System (IPFS) publisher image, reads the content identifier (CID) from that image, checks only that it has the bafy… form, and creates or updates the GitHub release with that CID in its notes. Confirm the release exists and records the CID before announcing.
  6. In the production UI release notes, state that ?simulate=1 is a browser-local sandbox. Mainnet and Sepolia quote-dependent actions use live RPC data plus available network-local Uniswap liquidity; simulation uses its configured mock where supported. Stale, unavailable, or unsupported quotes are production blockers for the affected client action, never inputs to replace with simulation prices. RPC and client integrity remain covered by A24; quote availability is an official-client limitation, not a protocol security assumption.

Review genesis REP allocations (Sepolia and deterministic testnets)

Sepolia genesis REP allocations are canonical source data in sepoliaRepAllocations.ts. The configured 11 million REP mint cap is divided equally among the listed holders; adding a holder automatically reduces every holder's allocation. Integer division may leave the total minted supply below the cap by less than one attoREP per holder. Review both the holder list and the computed total before deployment. The GenesisReputationToken constructor requires at least one allocation, matching holder and balance array lengths, unique nonzero holders, nonzero balances, and a total supply no greater than 11 million REP. It emits the standard ERC-20 mint Transfer event once for each allocation.

The sum of the constructor balances is immutable and is returned by the REPv2-compatible getTotalTheoreticalSupply() selector. There is no administrator, post-deployment mint, allocation correction, or recovery entrypoint. An incorrect allocation must be fixed in the source list before deployment and the deterministic manifests must then be regenerated. Because constructor arguments are part of CREATE2 init code, any allocation change produces a new genesis REP address and new addresses for every deployment step whose constructor wiring depends on it. Never continue a deployment from a manifest generated for a different allocation list. A future release that intentionally changes starting holders must follow the same source review and full-manifest regeneration procedure.
