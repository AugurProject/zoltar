Migrate through a fork

Identify the child universe the application intends to support, then apply the deadline and materialization rule for each position type. Zoltar represents the branch; it does not verify that the branch is the objectively correct answer. Not every position expires with the child-creation window.

Verify the fork

Confirm the parent universe's fork question, outcome encoding, fork time, valid child identifiers, and the pool's own fork-activation state. Verify that fork activation automatically materialized the parent's deterministic pool migration proxy; it is not a separate migration-window action. A Zoltar fork does not by itself prove that a particular pool has completed its snapshot transition.

Choose the branch

Evaluate outcome evidence independently and choose the intended child universe. Record the exact child identifier. Migration expresses branch support and can have irreversible economic consequences; do not infer the branch from display order or an unverified interface.

Choose the procedure from the asset

  • Raw Zoltar REP held by a user: approve Genesis REP when required, call addRepToMigrationBalance(universeId, amountAttoRep), then splitMigrationRep(universeId, amountAttoRep, outcomeIndexes). The exact ABI name is outcomeIndexes; use it consistently in the request and reconciliation record.
  • REP already locked in the security-pool migration proxy: call migrateRepToZoltar(pool, outcomeIndices).
  • Ordinary vault: the vault owner calls migrateVault(pool, outcomeIndex) within the pool-local migration window.
  • Unresolved escalation: the vault owner calls migrateVaultWithUnresolvedEscalation(pool, vault, childOutcomeIndex); entitlement initialization is lazy inside this call.
  • Direct escalation deposits: the vault owner calls claimForkedEscalationDeposits(pool, vault, outcome, depositIndexes).
  • Missing child: ordinary vault and unresolved-escalation migration lazily create the destination on first use; an explicit createChildUniverse(pool, outcomeIndex) call is optional, while multi-target share migration still requires an existing destination before its deadline.
  • Shares: the share holder calls shareToken.migrate(fromId, targetOutcomeIndexes); an existing child can materialize after the pool window, while creating a missing destination remains deadline-gated.

Migrate each position

Position or action Time rule Verification
Create a missing Statoblast child pool Must occur within the pool-local eight-week migration window. Confirm the deterministic child identifier, parent pool, and deployed code.
Split raw Zoltar migration REP Direct Zoltar migration uses its forked-universe balance rules; the security-pool wrapper migrateRepToZoltar(pool, outcomeIndices) remains deadline-bound to the pool-local migration window. Verify whether REP was burned into a user migration balance or split from the pool proxy, then verify child REP.
Migrate REP backing units and associated pool-held vault REP backing Use the Statoblast pool-local migration window and REP-backing-unit checks. Compare parent deltas with child REP backing units, coverage commitment, REP, and collateral.
Claim direct own-fork escalation deposits Use the own-fork claim window and require an unpriced child branch. Verify the authenticated depositor, outcome, consumed source claim, and child REP recipient.
Materialize shares into an existing child No expiry after the child exists; creating a missing destination remains deadline-gated. Verify the source entitlement, child share balance, and replay protection.
Settle carried escalation claims Follow the child continuation lifecycle and proof rules rather than treating the claim as ordinary vault migration. Verify the parent snapshot, carry proof, immutable depositor, and settlement state.

FORK-05 is the canonical deadline and post-deadline share-materialization rule.

Reconcile the child

Compare migrated REP, collateral, open interest, REP backing units, coverage commitment, shares, and carried escalation totals with the parent deltas. Use VaultMigrationCheckpoint, PoolHeldRepSweptToChild, and child-game events as the evidence. Expect collateral to follow migration rather than appear in full in every child.

Retry safely

Migration calls are state-dependent. After a reverted or dropped transaction, inspect the child, source entitlement, and claimed/materialized flags again. Retry only the missing procedure; never replay a successful migration based on a stale UI balance. Choices that select a child or consume a claim are irreversible at the protocol layer.

Complete child recovery

After the window, determine whether the child needs a truth auction and whether a paused escalation continuation can resume. Do not reopen normal operation until the child satisfies its lifecycle and backing gates.
