Trace a fork into child recovery

Use the seeded fork-auction fixture to trace the first parent pool into its materialized Yes child, then distinguish migrated value from remaining repair obligations.

Open the fork scenario

Continue with the Security pool x2 auction simulation at http://localhost:12345/?simulate=1&simScenario=securitypoolx2-auction#/security-pools?securityPoolsView=browse. From the pool registry, choose Will this resolve? (securitypoolx2 #1).

Checkpoint: the first parent is forked while the second seeded pool remains a separate lineage.

Inspect the parent snapshot

Record the parent universe, open interest, settlement collateral, vault REP backing, and available outcomes. The fixture minted complete sets before the fork and deliberately left some REP unmigrated, so the parent remains the source of child entitlements rather than silently choosing one answer.

Open the materialized child

Follow the Yes branch to its existing child pool. Confirm its parent address and outcome. The fixture materializes Yes only; a child address can be deterministic before deployment, but an absent child is not equivalent to a deployed pool.

Checkpoint: the selected child is the Yes branch and has its own universe and pool lifecycle state.

Trace the migrated assets

Compare parent and child REP, vault state, open interest, and collateral. The fixture migrates REP to the Yes universe but leaves enough parent value behind to require repair. Collateral follows migrated economic claims rather than being copied into every possible child.

Checkpoint: child backing is not a duplicate of the complete parent snapshot.

Inspect the repair boundary

Open the child's fork-auction view. Confirm that a truth auction is active with ten seeded bids at three price levels. The auction raises as much repair ETH as supported demand provides; it does not determine which universe is true.

Checkpoint: the child is in repair rather than normal operation, and auction finalization is still a separate transition.

What you learned

You followed state and assets across an explicit branch rather than imagining that a fork copies all value. Use the production migration guide when performing the task, and read Zoltar and branching truth for the underlying model.
