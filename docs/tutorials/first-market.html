Explore a seeded market and security pool

Use the deterministic Security pool fixture to connect one binary question to its pool, funded vault, complete-set shares, and accepted oracle price. This tutorial inspects known reachable state; it does not pretend the fixture contains a completed market lifecycle.

Before you start

Build and serve the UI, then open http://localhost:12345/?simulate=1&simScenario=security-pool#/security-pools?securityPoolsView=browse. Wait until the simulation banner names the Security pool scenario. Simulation executes resettable transactions against local fixture state; it does not send them to an external chain or require an external wallet.

bun run ui:build
bun run ui:serve

Inspect the question

Open the pool whose question is Will this resolve?, then inspect its market summary. Confirm that it is binary, has Yes and No outcomes, and ends in the future. The question belongs to Zoltar; the tradable and underwriting state belongs to the Statoblast pool built around it.

Checkpoint: the browse view contains exactly one seeded pool for that question.

Inspect the security pool

In the selected pool, compare settlement collateral, open interest, REP backing, and the vault directory. Open the seeded vault and confirm that it has positive vault REP backing and an active coverage commitment. A complete set consists of one share for every outcome and is backed by ETH; the vault's REP supports pool capacity rather than one trade.

Checkpoint: the pool has one funded vault and is operational.

Inspect complete-set capacity

Open the pool's trading view and record the baseline complete-set collateral, share supply, and remaining mint capacity. A creation mints one share for every outcome together; redemption consumes a complete outcome set. Compare these values with the post-transaction state in the next step.

Checkpoint: mint capacity is derived from fee-eligible coverage commitment rather than from the displayed REP balance alone.

Mint one resettable complete set

Use the preselected Simulation QA account, choose the smallest enabled amount, and submit Mint complete sets. Record the amount submitted, ETH balance before and after, each outcome-share balance and total supply before and after, and every field of CompleteSetCreated. Each outcome-share balance and total supply must increase by exactly the submitted complete-set amount.

Reset by refreshing the simulation URL or restarting the UI server. The expected post-reset checkpoint is the original seeded vault and share supply.

Inspect the reporting boundary

Open the reporting view. The seeded question is still live, so reporting is not yet actionable and there is no active escalation game. This is the boundary to remember: the market end time must pass before outcome reporting begins.

Checkpoint: the interface keeps reporting actions unavailable while the question is live.

What you learned

You connected the seeded question, pool, vault, shares, and reporting boundary without assuming state the fixture does not contain. Next, inspect a completed escalation fork or continue to the protocol explanation.
