Subsystem guardrails

Check these subsystem boundaries before sending a transaction. See the security model for external assumptions and the invariant catalog for cross-contract properties.

Security pool capital operations

Every question belongs to a shared security pool. Verify the factory registration, capital ledger, settlement module and universe before sending funds. Deposits add principal; setting a commitment separately authorizes risk. Withdrawals and retirement check current owner principal and demand. Complete-set purchases use the registered security pool route and recheck fees, available healthy capacity and backing floor.

Before Liquidation takeover, deposit backing REP and set a health target. Verify the funding caps, price epoch, health target and retirement cohort. The reward goes to the receiver vault. See how takeovers and cures work and the capital ledger reference.

Share migration

Share tokens retain one question lineage and separate outcome balances per universe. A forked source uses its canonical child question. Activate the shared branch with prepareBranch, startBranch and finalizeBranch before migrating shares into it; until then ShareToken.migrate reverts with Fork branch not active instead of running that work inside the migration. In an active branch a single-target migration materializes a missing child question itself. Finalized claims retain protected source settlement; do not assume every source claim must migrate.

See ShareToken entrypoints for migration and recovery calls.

Reporting and settlement

For reports through the question ledger, approve wallet REP to that ledger; direct deposits into an existing Escalation Game require approval to the game. The accepted deposit enters separate reporter custody and never becomes provider capital. Finalized local claims use deposit indexes; inherited claims use authenticated frozen-leaf proofs. Payouts go to recorded owners. Batches can be split, and deep lineage proofs use bounded preparation transactions.

See Escalation Game entrypoints for deposits and claims.

Shared forks

Owners choose one branch before the native cutoff. The shared coordinator snapshots and prepares each chosen branch once, then lazy owner activation and question materialization apply that state. A missing keeper cannot extend choice or auction deadlines.

See the shared fork processing reference for branch preparation.

Collateral repair auctions

The branch auction sells fresh unchosen provider REP against its aggregate collateral shortfall. Buyers bid lots of the security pool’s collateral token with minimum REP-per-lot limits; there is no limit on bids per address. Winning backing and commitments enter aggregate accounting immediately at closing. The auction reference describes how bids are claimed. Claiming is not required to count the winner’s obligation, but a bidder with any unclaimed bid cannot choose a branch in a later fork, so claim every bid of a bidder, including losing ones, before its fork choice. Each bid’s unused collateral is refunded once to its bidder through refundBid, independently of claiming.

See the Collateral Repair Auction reference for bid and refund calls.

REP/collateral price reports

Verify that the report sponsor can fund its collateral, REP and settlement bounty separately from provider capital. A pending report does not block independent candidates. Capital operations recheck price, owner authorization, health and exposure. See sponsor-authorized operation batches for report-bound calls.
