Reference

Contract inventory

This page lists every production Solidity source by area. The contract interaction reference documents the entrypoints of the contracts users and keepers call; this page adds the caller and trust boundaries of the deployment helpers, delegate modules, and libraries that reference does not cover, and the Uniswap contracts a testnet deployment uses.

Caller and trust boundaries

Deployment helpers are not interchangeable with canonical protocol discovery. Several are intentionally permissionless and bind the caller into each deployed address, through a caller-namespaced salt or the caller in the init code; an application must discover canonical instances through SecurityPoolFactory, recognized question ledgers, and recognized question forker events rather than treating every factory-created address as canonical.

Module Direct caller boundary Canonical-use boundary
SecurityPool SecurityPoolFactory.deploySecurityPool(creationCode, configuration) is the only way to create a security pool the factory recognizes: it deploys the pinned creation code with the factory and its pinned module deployers, and records the result in isSecurityPool. The creator chooses only the configuration: an immutable ERC-20 collateral token, positive collateral report stake floor, admission policy, question horizon, economic configuration. After construction, four permissionless prepareNext() transactions initialize settlement, reporter/fork modules, capital, then the shared feed and activation. setupStage == 4 is required before accepting user funds or risk. Anyone may register an allowed, open question in the unforked origin universe. After the origin forks, this security pool cannot admit new questions in any branch; see question admission after a fork. getQuestionLedger(questionId, universeId) resolves the registered lineage through the configured factory. Each universe has one capital ledger and one shared REP/collateral feed. The central settlement book owns question cash and supply accounting; the capital ledger owns each provider’s REP and commitments; the reporter ledger separately owns report escrow. Native question contracts expose shares and reporting. Verify isSecurityPool on the canonical factory and the module bindings independently. See the security pool model.
Question admission policies ISecurityPoolQuestionAdmissionPolicy.isQuestionAllowed(securityPool, universeId, questionId) is a read-only approval check. SecurityPoolOpenAdmissionPolicy always approves. SecurityPoolFixedAdmissionPolicy(universeId, questionIds) fixes a nonempty, duplicate-free list at construction with no mutation authority. Its paginated getter returns at most 64 entries. Policy approval is required for registration and purchase, including reuse of a registered question. Denial or a failed policy call does not block exits, claims or fork recovery. The UI offers the open and fixed policies; the contract API permits other policies.
Security pool economic configuration EconomicsConfig fixes purchaseFeeBps (at most 10,000), annualFeeBps, minimumPurchaseFeeAttoEth, positive minimumCommitmentAttoEth, minimumOutcomeRate, positive rewardVestingSeconds (at least 24 hours) of at most MAXIMUM_REWARD_VESTING_SECONDS (3,650 days). Read these immutable settings from the security pool’s corresponding getters. The creator supplies the security multiplier in OriginConfig.securityMultiplierBps. Each provider selects its own health target through setHealthTarget. Raising it on a live position requires a fresh price and sufficient backing. depositAndSetHealthTarget(amount, targetHealthFactorBps) adds REP and updates the target atomically, applying the same backing check to live target increases. Lowering a target does not increase commitment. The protocol’s liquidation requirement remains unchanged.
SecurityPoolCapitalLedger: provider accounts depositFor(owner, amount) is callable only by that owner and adds REP to their entire live position, or to idle principal when they have no commitment. setCommitment(commitment) sets the owner’s whole collateral commitment K, backed by all deposited REP C. Without a pending retirement request, raising or keeping K applies at once, subject to a fresh price and the owner’s health target; a raise must also fit the accepted report’s funded exposure limit. setCommitmentWithReport(reportId, commitment) can instead prove coverage for a raise using a fresh report the shared feed accepted. Its conservative collateral floor stays attached to the owner until the next canonical price epoch, which must cover actual aggregate exposure. Each owner has at most one live position per security pool and universe, active or retiring, with exact C/K amounts. ownerCollateral(owner) returns deposited principal, commitment and currently withdrawable principal, excluding collateral and REP earnings. The chosen health target controls authorization, takeover receipt and pledged-principal withdrawal. Liquidation uses the protocol floor, whose security multiplier is at least 10,500 basis points.
SecurityPoolCapitalLifecycleDelegate All capital ledgers in a security pool share a lifecycle delegate for authorization, owner withdrawals, earnings claims, and fork-choice export, import, and backing release. The ledger calls it through delegatecall, using its own storage layout from SecurityPoolCapitalState. Direct calls to delegate mutation entrypoints revert. The ledger’s entrypoints retain caller permissions, reentrancy guards and price/checkpoint requirements. Principal and earnings stay in the ledger. Preparation reports cache prices without starting imported positions’ health history. finishForkImport seals the funded imports and records a health observation only if the cached price is still valid. The capital implementation pins the security pool’s lifecycle and auction delegates.
Principal withdrawal and retirement withdrawPrincipal(amount, recipient) withdraws idle principal without a price requirement. A live position must be unforked and have a fresh price; its remaining REP must cover K at ownerConservativePrice(owner), the protocol multiplier and the saved health target. That price includes an unexpired growth-proof floor when present. Lowering K with setCommitment at a fresh price can cure an uncovered deficit immediately when it meets the economic minimum and capacity permits; a smaller deficit queues the whole reduction, for partial and full exits alike. At a stale price the whole reduction is queued. Zero requests a full exit; a nonzero residual and the queued reduction must each meet minimumCommitmentAttoEth. The owner cannot change or cancel a pending request through setCommitment: until it is served, setCommitment accepts only the pending value, which leaves the request in place and cures an underwater position at a fresh price. Retirement requests are FIFO by immutable request number, independently of health ordering. Adding REP cannot improve priority. Anyone may call serveRetirement(positionId); it serves exactly that position’s own request when ready, and the released principal stays with its owner. Principal withdrawal also attempts the owner’s ready request. No call processes positions other than the one named, but an owner cannot leave a ready request reserving spare capacity that its ineligible position no longer supplies. A later owner may complete before earlier owners claim only when spare healthy capacity reserves every earlier requested reduction and their own full healthy reduction. Partial retirement retains all C and returns the residual K to active status; a full exit releases C to its owner. Request sums use a uint64 Fenwick index with at most 65 storage slots per update and 64 per prefix query, independent of queue length. The healthy commitment tree remains separate. Imported fork choices preserve request numbers. Transferring to a new queued receiver, or adding commitment to a queued receiver, places its request at the tail; backing-only top-ups preserve order. previewRetirement(positionId, acceptedPrice, demand) reports readiness and reserved reductions ahead. It is advisory: price, demand and fees are rechecked at execution. New purchases can use healthy active commitments and retained portions of pending requests, without consuming requested reductions.
Purchases, redemptions and earnings createCompleteSet(universeId, questionId, cashAttoEth, recipient, minimumShares, maximumFee) requires admission and fresh healthy capacity. Every purchase pays the larger of the flat minimum and the backing-based fee, plus a prepaid resolution premium. purchaseQuote(universeId, questionId, cash) returns the complete fee and its premium component; purchaseFee(cash) returns the base fee including its flat minimum, without the premium. Capacity must cover purchase cash. Ordinary holding fees continue past calendar end until reporting starts or funded units exhaust. The buyer approves the security pool services contract. The transaction transfers cash plus the actual fee in the selected token, rejecting any fee above maximumFee; no unused budget is transferred. quoteMintRecoveryRep(universeId, questionId, cash) quotes the separate REP contribution needed when that question already holds inherited recovery REP. createCompleteSet authorizes no REP spending; use createCompleteSetWithRecoveryRep with the same arguments plus maximumRecoveryAttoRep to fund that contribution. The buyer approves the canonical settlement contract for REP, separately from the service contract’s collateral allowance. The supplied REP belongs only to the purchased question’s claims and preserves existing holders’ REP per share. Redeeming complete sets reduces that question’s cash and aggregate backing demand; the purchase fee is not refunded. Released capacity can serve retiring providers without a claim for every question. Earned fees accrue through aggregate indices; the base purchase fee and reporter surplus vest over the configured duration. A healthy position earns its fraction of total K, including unhealthy K in the denominator. Unassigned collateral and REP are burned. claimEarnings(recipient) pays the owner’s collateral and REP earnings to a recipient the owner chooses, so a token that refuses the owner cannot strand them. Collateral transfer failures do not block fee checkpointing or REP operations. Capital calls services’ withdrawCapitalCash() when a payout needs funds; only services can call settlement’s withdrawServiceFees(). Permissionless flushBurn() on capital and flushBurn(universeId) on services retry quarantined burns. A failed payout reverts and leaves its funded claim available for retry.
SecurityPoolCapitalFeeStreams The deployer initializes the clock and rewardDuration when it creates the clone. The bound capital ledger holds the assets and can call addStream(ethAmount, repAmount) to fund a schedule after checkpointing. Equal-second additions share an endpoint; later funding appends a cumulative checkpoint. Lookup excludes released history and searches at most 48 timestamp bits, with the live range bounded by the duration. checkpoint(eligibleThrough) separates releases before and after the eligible cutoff. After a price has been accepted, prepaid streams keep vesting at the last accepted price through stale intervals, with old weights checkpointed before each mutation. Income without eligible backing is quarantined: REP burns immediately and collateral enters pendingBurnCash. It never restarts those amounts for future providers. fundedOutstanding() returns scheduled, unreleased income. Forks preserve existing dates and credit eligible frozen parent commitments at the last accepted price; unassigned parent income burns. Principal and earned claims are excluded.
SecurityPoolSettlementBook: claim units and cash pricing Settlement starts with UNIT_SCALE = 109 claim units per raw collateral unit. Later purchases pay the current net cash value per unit, including cash retained through redemption rounding. question.units and totals.units are claim weights divided by that scale and rounded up; they are not cash valuations. scaledQuestion, scaledUnits, scaledAvailableFeeBudget, books and frozenBooks expose full-precision weights. The public question view converts fee principal to raw cash and fee rate to raw cash multiplied by UNIT_SCALE per second. The corresponding scaledQuestion fields remain in claim units. Use isCashFunded, requiredCash and requiredForkCash for backing decisions instead of comparing cash with claim weights. validateMintFeePrecision rejects positive-fee purchases whose rate would be zero or lose at least one raw cash unit per year through truncation. Premium weights retain their own fractional precision; fork recovery uses full-precision settlement weights.
SecurityPoolServices and SecurityPoolResolutionPremiumBook The service module owns prepaid resolution premiums. It holds no shared budget for keepers or price sponsors. Each question earns its premium only during its funded unresolved interval. A persistent expiry index removes earned units and burns the unused terminal remainder without scanning questions, because the book does not record which buyer paid it. Changes checkpoint earned income under the capital ledger’s old weights. Reporting updates replace only the affected question’s schedule. A stream never runs past the 52-day prepaid window. Forks copy the schedule roots and divide funded cash by chosen commitment; they do not replenish it. A child whose share is zero, or so small that the inherited units exceed 10¹² per unit of cash, starts with an empty premium book, and that share is burned. A surviving child therefore prices new premium at about 1021 full-precision units per unit of cash at most, and its premium unit domain of 2208 full-precision units holds about 2138 raw collateral units of premium even at that ratio. Before imports become operational, the fork coordinator calls checkpointPreparationPremium(child) to burn elapsed inactive premium and any unused terminal remainder. The security pool authenticates native question ledgers, reporters and accepted price reports. The service module credits already-earned capital fees without moving collateral and records each ledger’s pendingCapitalCash. Settlement retains collected fees in pendingServiceFees until the service module withdraws them for an earnings payout or burn. withdrawCapitalCash() pays only the calling ledger’s assigned income; flushBurn(universeId) moves queued unused premium independently. The service module can fund vesting streams and synchronize demand; it cannot change the accepted price or withdraw provider principal.
Personal liquidation and bounded accounting Apart from an embedded takeover cure, only the owner cures through setCommitment. takeOver(positionId, commitment, minimumTakeoverReward, maximumOwnRep) enforces the requested minimum takeover reward. After an unpaid cure at the conservative repair price, it transfers a takeover reward from the source’s pledged REP that grows linearly to all of it over one hour and sizes the commitment using the source’s backing after the takeover reward at the conservative price. Smaller fills receive a proportional takeover reward and consume cumulative vesting; they must either restore conservative backing completely or leave the source below the liquidation price so it remains repairable. Maximum terms remain available after one hour. Source principal moves only as the receiver’s pledged takeover reward; old earnings never transfer. A full replacement credits the source owner with any pledged REP not paid as the takeover reward. The receiver supplies remaining backing and earns future fees. A receiver’s resulting commitment must meet the economic minimum; an existing receiver may be active or in the source cohort. An active receiver does not inherit retirement intent; a queued receiver that gains commitment rejoins the request tail. takeOverWithBounds additionally pins price epoch, receiver health target and source cohort and caps resulting principal and commitment. Successful healing cures stand without a transfer. A cure cannot free nonzero principal, including when supported commitment rounds to zero; releasing it requires ordinary retirement. Pledged withdrawals require healthy commitment at least equal to demand. Free principal and earned fees are separate. Admission, fee eligibility and surplus withdrawals use price / (1 − error), rounded up; owner-requested cures and adverse observations use price / (1 + error), rounded down, where error is the configured oracle dispute target. Takeover eligibility uses the liquidation bound; the repair amount restores the source at the conservative bound. An owner’s health setting remains separate. Other providers’ C/K balances are unchanged by a target liquidation. Balanced trees index live commitments and health. Finality processing subtracts the previously processed prefix from the current timestamp prefix, using modular arithmetic only for historical totals; each pending deadline’s amount remains checked. SecurityPoolFrozenHistory appends one immutable checkpoint with constant work and resolves claims through at most 48 forest steps and 48 tree steps. Forks copy its head and the processed prefix. Work follows bounded paths and the owner’s single position, without scanning questions, providers or expired streams. Native share migration still requires one action per intervening universe.
SecurityPoolCommitmentIndex: liquidation accounting Only the bound capital ledger calls cure(id, price, multiplier, minimumCommitment, demand, target, ownerExit) or clearLiquidation(id). takeover checks eligibility, applies the conservative-price cure and quotes the transfer backed by the takeover reward in one call. The index updates commitments and records healthy observation epochs while the ledger retains custody. Any owner reduction queues without an immediate cure when its unsupported commitment is below the economic minimum, whether the requested exit is partial or full. Each accepted operating price stores one observation timestamp, without visiting individual owners; preparation prices do not start that history. liquidationStarted(id) derives the first adverse observation after the latest healthy epoch or fresh-price recovery mutation. It returns zero for healthy or retired positions. The capital ledger exposes the same getter. liquidationElapsed(id) counts wall-clock time, including stale-price gaps; a started auction remains executable at the last accepted valuation without renewal; liquidationPenaltyPaid(id) tracks the liquidation penalty already paid from the position during the same distress episode. No starter transaction is required; uninterrupted distress retains its original timestamp, including across stale-price deposits.
SecurityPoolForkCoordinator: choices choose(sourceUniverse, outcome) freezes and exports the caller’s single position and its entire deposit, including surplus collateral, into one selected branch. Idle principal without a remaining commitment and old earnings remain in the parent. Choices close eight weeks after the native fork. startBranch(sourceUniverse, outcome) then copies aggregate settlement and reporter roots and migrates REP once for that branch. Choices are immutable once exported and preserve the position’s retirement cohort, request number and requested remaining commitment. The native clock allows activation from week nine and prevents a child fork before week ten. Late preparation does not extend either phase. Parent cash is assigned as sourceCash × chosenCommitment / sourceCommitment, rounded down, independently of excess REP. Unselected child REP belongs to inherited outcome claims; the coordinator never chooses a branch on the owner’s behalf.
Shared branch claim recovery prepareBranch, choose, and startBranch can each freeze the source and create the child REP token and capital contracts as needed. The child capital ledger, commitment index, and fee streams are minimal proxies with branch-specific bindings. The shared price feed also uses a minimal proxy and can be prepared independently. startBranch migrates pledged REP and live recovery REP once, splits the requested child once, and assigns chosen collateral to its providers. Fresh unchosen backing may enter the branch auction; old recovery REP remains reserved for inherited claims. finalizeBranch creates the settlement book with assigned parent cash plus accepted auction collateral, installs funded winning commitments, and activates after the fixed deadline. Unsold REP joins claim recovery. An absent or stale price does not prevent activation; eligible holding-fee streams start only with a fresh price in an unforked child. Preparation reporting follows the fixed reporting window. The child settlement book preserves the inherited question units. Collateral redemption uses the question’s settlement units. REP has a separate Q128 entitlement accumulator and per-question corrections, so a partial claim receives its share of REP even when its collateral-unit burn rounds to zero. Finality freezes both entitlements. Live units and funded child REP are each bounded by uint128; cumulative REP indices use modular arithmetic across repeated forks. Each fork’s new REP is allocated by question units at that fork, so holding fees charged later in the child do not reduce an inherited question’s REP share. attoSharesToAttoEth and attoSharesToAttoRep quote the two assets through the native question ledger. Cash below the inherited funding target disables new minting and ordinary holding fees; recovery REP remains question-owned through funded minting. If no live claim units exist, surplus child REP is burned. Finalized source claims retain their source assets. SecurityPoolSettlement.topUp(universeId, maximumCashAttoEth) accepts a permissionless donation of the entire positive active cash deficit, read after checkpointing, and returns the amount pulled. It reverts when no deficit remains, the repaired demand would exceed total underwriting commitment, or the live deficit exceeds maximumCashAttoEth, so a redemption or finality that shrinks the deficit before inclusion does not invalidate the donation. It preserves all recovery REP and frozen claims; the sponsor receives no assets or commitments. Fully cash-backed books regain fee eligibility. quoteMintRecoveryRep(bookId, questionId, cashAttoEth) quotes the rounded-up REP needed to preserve an inherited question’s REP per share on minting, and reverts with Recovery REP too large when the book could not hold that REP below 2^128. The funded custody path pulls that REP from the buyer into settlement, bounded by maximumRecoveryAttoRep, and credits only the purchased question. Existing mint methods have a zero REP budget; fresh questions require no REP contribution.
Source recovery eligibility and rights ShareToken.isSecurityPoolRecoveryEligible(sourceUniverse) returns true only for a forked canonical security pool question with live source liabilities. The settlement book’s hasLiveForkRecoveryRight(bookId, questionId, forkTimestamp) requires outstanding outcome supply outside frozen claims. Before sealing, a nonzero finalAfter < forkTimestamp excludes the question once forkTimestamp > minimumFinalAfter, even if finality has not yet been checkpointed. After sealing, the frozen-claim assignment is authoritative. Protected finalized shares retain ordinary source question ledger redemption; transferring or consuming their recovery rights reverts with No live source recovery right. balanceOfSecurityPoolRecoveryRights(sourceUniverse, holder) returns unspent Invalid, Yes and No rights, or all zeros when ineligible; their minimum bounds complete-set cash recovery. Holders combine rights using transferSecurityPoolRecoveryRights(sourceUniverse, recipient, amountsAttoShares) without transferring source shares or child migration rights. recoverUnchosenCash(source, questionId, shares) consumes one right per outcome for each requested share. Protected finalized claims remain in the universe where they finalized.
Reporter custody and native question materialization SecurityPoolReporterLedger holds funded per-question report balances in persistent books. Only canonical games can debit their own balances. A fork charges admission to the triggering question only; unrelated report balances cannot fund it. Strictly finalized escrow remains in its source universe; live books migrate once per branch. QuestionForker.prepareSecurityPoolQuestion(source, targetUniverse) creates the canonical question namespace separately from materializeSecurityPoolQuestion, which installs at most one of three fixed outcome snapshots per call when needed; the question activates after the third. Bound questions do not deploy individual Collateral Repair Auctions or migrate provider vaults. Trader tokens retain their immediate-parent migration checks, so skipped native universes still need explicit token migration.
SecurityPoolUniformPriceRepairAuction Only its immutable controller starts bidding, submits funded bids, finalizes and settles refunds. Each lot contributes the same fixed collateral amount. Lower minimum REP per lot ranks first. The controller passes finalize(maximumFilledLots, floorAttoRepPerLot) and previewFinalization a floor f, a multiple of the grid (Auction floor must use the REP price grid); zero applies none. For inventory I, finalization selects the largest available prefix of F lots, capped by target lots, whose marginal minimum m satisfies F × max(m, f) ≤ I. The floor never changes which bids rank first. Clearing REP per lot is q = max(m, f) and sold REP is F × q, including below target. With no feasible lot, the sale is zero. Bids cannot be cancelled. Each winning lot pledges q REP. Unsold REP I − F × q remains for inherited claims; it does not become winner fee credits. Equal-price bids rank by submission order, so winners are exactly the first F lots in price-then-submission order; at most one bid, the earliest unfilled one at m, fills partially, even when q > m. The engine holds bid collateral; the controller holds sale REP. Refunds are pull credits for the bidder. Before finalization, earlyRefundAttoEth returns the full bid collateral only when the demand ranked before it (lower limits and earlier bids at its limit) B ≥ min(T, ⌊I / p⌋), where T is target lots and p is the bid’s minimum REP per lot; otherwise it returns zero. Settled, unknown and finalized bids return zero. Refunded bids remain in the tree, permanently outside every winning prefix. The same exclusion condition rejects a new bid at submission, counting every existing bid at its limit as ranked before it. maximumAdmissibleBidAttoRepPerLot() returns the highest grid-aligned limit a new bid can submit against the current book, or zero when none is admissible; SDK quotes and approval guards apply that bound. settleAndWithdrawRefund lets the controller credit one of a bidder’s own refund-eligible bids, unless already credited, and pay that bidder’s entire credit in one transfer; it reverts when nothing is payable, and a rejecting recipient reverts the new credit while older credit stays withdrawable. After finalization, nextUnmaterializedBid(afterBidId) returns the next winner still sharing fee ownership in price order. Zero starts a sweep and also marks its end. A nonzero cursor is excluded from the result and remains valid after its winner is materialized. Zero-weight subtrees skip both losing and detached bids without a history scan. Clearing, individual settlement and fee allocation use logarithmic tree paths without scanning bidders; numeric escrow and fee budgets are bounded by uint128.
SecurityPoolRepairAuction The fork coordinator deploys one controller per eligible branch. It sizes equal collateral lots of lot = ⌈shortfall / ⌊shortfall / minimumCommitmentAttoEth⌋⌉ and offers ⌈shortfall / lot⌉ of them, so their total covers the entire shortfall without requiring it to divide evenly; an auction exists only when the shortfall is at least one minimum commitment. Finalization forwards at most the shortfall to the fork coordinator and burns the rounding surplus of a full fill, which is less than one raw unit per lot. At opening, it can reduce the lot count and enlarge each lot until REP-grid rounding adds less than 1% to the unrounded backing requirement. A single full-shortfall lot may exceed that rounding limit when REP indivisibility requires it. Read lotAttoEth and targetLots after opening for the final bid units. Each bid pulls exactly its whole-lot collateral amount from the bidder. The bidder must approve the auction controller to spend that ERC-20 token. Lots and amounts use raw collateral units. No REP deposit or REP approval is required. The minimum REP per lot must cover requiredRep(lot, openingConservativePrice, M, health), where M is securityMultiplierBps and health ≥ 10,000 is the chosen target in basis points. This rounds upward after multiplying lot collateral by price and dividing by 10¹⁸, then after applying M / 10,000, then health / 10,000. Bid minima must be positive multiples of grid = M / gcd(M, 10,000) and cannot exceed inventory rounded down to that grid. There is no seller price floor or auction reserve-factor setting; the closing floor below is a minimum REP per lot. Opening requires at least one day before the fixed close, a fresh funded branch price and enough inventory to back one lot at 100% health, rounded up to the grid. The fixed week-nine close uses the last accepted quote only if its settlement-eligibility timestamp lies within the final day; it need not still be fresh at the exact closing second. The sale is cancelled if the universe forked at or before the deadline, no such quote exists, or its accepted exposure limits no longer cover the security pool’s oracle exposure and the inventory. Otherwise the controller finalizes with a floor of requiredRep(lot, closingConservativePrice, M, 10,000) rounded up to the grid: every winning lot receives at least that REP, and fewer lots fill when the inventory cannot provide it. A closing price above the opening price does not cancel the sale; the bidder’s health target applies only at the opening price. Finalization delivers all sold REP into capital; winning commitments equal accepted bid collateral. Pledged REP and fee rights enter aggregate accounting immediately, independent of individual materialization or refunds. settleRefund lets anyone credit a provably excluded bid before finalization, or settle the final unfilled-lot refund afterward. Only the bidder can withdraw its credits, to a recipient of its choice, separately or combined with crediting one of its own eligible bids through settleAndWithdrawRefund; the combined withdrawal includes credits from the bidder’s other bids. Unsold fresh REP and all old recovery REP remain for inherited claims. Sub-lot shortfalls do not open an auction; the full-deficit donation described above can repair them.
SecurityPoolRepairAuctionVault and SecurityPoolCapitalRepairAuctionDelegate Each bid creates a separate vault controlled by its bidder: a minimal proxy to the one implementation the auction deployer publishes, with the bidder, initial ledger, auction and bid identifier fixed in the clone’s own code and the bid identifier as its CREATE2 salt. Each clone keeps its own storage, so per-bid liability isolation is unchanged, and the implementation refuses direct use. Winning principal and commitment first share one protected capital position. materializeRepairAuctionBid splits one exact funded entitlement, preserving health history and historical fees; it pays no keeper reward. The bidder’s vault materializes before its first voluntary operation and then records a permanent flag, so later operations skip the auction lookup and the ledger call; the flag only covers the initial capital ledger, child-universe ledgers after a fork keep their own checks, and it is never set for a zero fill. depositPrincipal pulls approved REP from the controlling wallet. executeAndSweep executes an owner-authorized call and returns the selected collateral, chosen token and ETH balance to the selected recipient. Unmaterialized winners count toward capital, fees and fork snapshots. They cannot avoid liabilities by delaying an individual claim. A winner’s bidder cures through its vault with setCommitment; takeOverRepairAuctionBid repairs only the affected position, moving the takeover reward from the position’s pledged REP into the receiver’s vault. Bidding requires no ETH execution reserve. Materialization alone earns no reward. Each vault retains an independent health target, liquidation liability and future branch choice.
Security pool module deployers SecurityPoolModuleDeployers deploys the capital implementation during security pool setup. Its commitment-index and fee-stream deployers each create a shared implementation at construction. The capital-ledger deployer shares one stateless lifecycle delegate; the fee-stream deployer shares one stateless auction delegate. Each security pool retains separate capital implementations and storage. The capital, settlement-book, service-accounting and fork-coordinator deployers use SecurityPoolCreationCodeDeployer to store creation bytecode in two immutable, STOP-prefixed CreationCodeChunk contracts through the common CreationCodeStorage primitive. The factory pins all nine deployer addresses and supplies them to every security pool it creates. Deployment permission does not grant authority over another security pool’s modules. Canonical bindings and initialization must be verified before use. These deployment boundaries keep creation code and individual initialization transactions within EVM limits.
EscalationGameFactory Anyone can call prepareEscalationGame(questionLedger) to deploy an unstarted game bound to that question ledger. The ledger must expose repToken() for preparation and for escalationGameAddress(questionLedger), which computes the deterministic address. The factory owns the game and starts it through deployEscalationGame on the ordinary reporting path or deployEscalationGameFromFork on the continuation path. Both start paths require the calling question ledger to have a bound reporter security pool and can reuse a prepared game. Ordinary deployment requires a threshold above one attoREP and lowers a start bond at or above that threshold to threshold - 1. Its constructor receives the separately deployed deposit delegate and requires code at that address. Games share this immutable helper while keeping their own accounting through delegatecall. Deploying the deposit delegate separately keeps factory init code within the EVM limit. The factory has no owner role and no later resumeFromFork relay. Accept a game only after EscalationGameSet from a recognized question ledger. In the supported continuation path, the owning question ledger calls resumeFromFork, which also verifies aggregate funding.
ShareTokenFactory Anyone can call deployShareToken to deploy or retrieve a token keyed by keccak256(abi.encode(msg.sender, salt, questionId)). The CREATE2 salt is the raw salt; the caller and question id enter through constructor arguments, and that caller is the token's initial authorized address. Origin lineage tokens are the instances created by SecurityPoolFactory and named in DeployQuestionLedger; children reuse the parent's token.
OpenOraclePriceCoordinatorFactory Anyone can call deployOpenOraclePriceCoordinator under a caller-namespaced salt with caller-supplied OpenOracle, REP token, and positive initialReportPriorityFeeAttoEthPerGas; coordinator construction rejects zero and values that would consume the reserved OpenOracle uint128 report and escalation-halt capacity. The caller therefore chooses this immutable gas-price assumption within that bound. A question ledger coordinator is the instance named by canonical DeployQuestionLedger; SecurityPoolFactory atomically binds it to that question ledger before returning, and canonical child deployment inherits the value from the parent coordinator.
PriceCoordinatorDeploymentWorker and QuestionLedgerDeploymentWorker Deployment workers split large creation code into deployable modules and bind the calling factory. Use canonical factory registration and module bindings; code presence alone is insufficient.
QuestionLedgerDeployer and QuestionLedgerDeploymentWorker Only the configured SecurityPoolFactory may call the deployer; only that deployer may call its worker. They are code-size deployment plumbing. The proxy deployer deploys one deterministic QuestionLedgerOperationsDelegate, and its address is passed into the SecurityPoolFactory constructor. The proxy deployer is the deterministic CREATE2 deployment proxy that every canonical deployment goes through; it is not a Solidity source in this repository and appears in the deployment manifests as step proxyDeployer. The factory passes that address through its deployer and worker to every question ledger. Its deterministic address is published as questionLedgerOperationsDelegate. Question ledgers become canonical only when the factory emits QuestionLedgerRegistered and DeployQuestionLedger.
EscalationGameDepositDelegate, QuestionForkerDelegate, QuestionLedgerSettlementDelegate, and QuestionLedgerOperationsDelegate EscalationGame delegates share game storage and implement reporting deposits and authenticated historical claims. QuestionLedgerOperationsDelegate handles wallet reporting, continuation resumption, and redemption. QuestionForkerDelegate prepares child questions against shared branch state. These helpers execute in their recognized host context. Accept resulting state and logs only when the recognized game, question ledger, or forker executes the matching wrapper through delegatecall. State changes and events then occur in that recognized contract's context. Canonical liquidation enters through the security pool capital ledger; continuation activation enters through QuestionLedger.resumeForkedEscalationGame.
QuestionLedgerAccountingModule A fixed delegate shares the question ledger storage layout and handles central fee checkpoints, surplus transfers and settlement mirrors. Only events from canonical question addresses describe protocol state. Calling a helper directly does not mutate a registered question.

Internal arithmetic

SecurityPoolUtils.calculateInitialEscalationDepositAttoRep is an internal pure function that derives the first-report bond from theoretical REP supply. It needs no deployed library or linking. Other lifecycle and underwriting math belongs to the corresponding security pool module.

UniverseIds.sol derives child-universe IDs from the parent and outcome. OraclePriceMath.sol centralizes conservative and liquidation price bounds and the report-priority-fee ceiling.
