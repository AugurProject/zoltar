1. How to use this spec

  • Open any file in mockups/ directly in a browser (no server needed). Each screen is static HTML styled by mockups/mock.css; shell.js, portfolio-head.js, mint-form.js and price-report.js inject the shared header, the security pool page head, the mint form and the price-report component so that every screen shows them identically.
  • The mockup scripts are mock scaffolding, not code to port. Port the behaviour described here into the existing Preact components; do not copy mock.css wholesale. Reuse the app's existing design tokens and primitives and match the mockup's layout, hierarchy and wording.
  • Dashed boxes labelled “Design note” or “Open question” are annotations for implementers. They never ship as product text.
  • Numbers in the mockups are one consistent example data set (canonical data), so screens can be compared. Real screens compute them.
  • Screen numbers (02, 04e, 12b…) match the mockup file names and are used throughout this page. Some file names still say “portfolio”; the product name is security pool (contracts SecurityPool and per-question QuestionLedger).
  • Start at 00 Feature map: it lists every feature of today's UI and where it lives in the redesign, so nothing is dropped. 19 Refresh plan is the data-loading plan.

2. Product decisions (fixed)

These were decided with the product owner. Do not reopen them during implementation.

  1. No global lists. No screen lists questions, security pools or price reports that anyone can create. Users reach things by link, address, question ID inside a security pool, or their Watchlist. Spam can never reach the screen.
  2. No Home page and no Questions tab. A question exists only inside a security pool (the same question ID can be registered in any number of security pools, each with its own shares and reporting). A question is always addressed as (security pool, question ID).
  3. Primary navigation is Watchlist and Price reports. The universe switcher is a menu in the header.
  4. The UI never reads event logs. No eth_getLogs, no event watching, no fromBlock scans. All information comes from contract state reads (see Data loading).
  5. No new contract indexes. No per-account or per-deposit index contracts or storage are added for the UI.
  6. The Watchlist holds only saved items (★) plus a short recently-opened history; no app-shipped suggestions.
  7. Question pages are full width (no right-hand side column). The universe fork action appears only when the escalation game has reached the fork step (04e).
  8. Less text. Communicate visually (bars, timelines, before → after rows, status dots) and keep only text that changes a decision. Safety-critical facts (irreversible, amount at risk, deadlines, forfeits, liquidation consequence) are always visible, never only in a tooltip or a closed disclosure.
  9. Addresses are shown in full whenever they fit; only when there is no room are they shortened, never wrapped (rule).
  10. Inputs never move or grow while typing; status, spinners and hints live in fixed-size slots.

4. App shell

Header (every screen)

  • Left: logo, tabs Watchlist (★) and Price reports. Question and security pool pages highlight Watchlist. Phones: tabs move to a bottom bar.
  • Right: REP price chip (1 REP = 0.0045 ETH), universe menu button, wallet chip, Activity, Settings. The right group wraps to a second row when it doesn't fit (never runs off-screen).

Universe menu (02e, 02f)

  • A button showing the current universe path (Augur v2 › Yes) opens a non-modal popover (role="dialog", no aria-modal) of ordinary links and buttons, not an ARIA menu. Esc closes it and returns focus to the button. On phones it is a bottom sheet over a scrim, aria-modal="true", focus trapped, visible Close button.
  • Content: current universe (id, status badge Active/Forked, your REP there), its parent if any, child universes after a fork (Created / “Not created yet”), and a Migrate REP… action when there is REP to migrate. “All universes” links to 15.
  • The button shows an alert dot when the current universe forked, or when you still hold REP in a forked parent (02e: 1 250.00 REP unmigrated). There is no REP migration deadline; say so.
  • The popover uses an opaque surface (not translucent).

Fork banner (02b, 12, 15…)

When the current universe has forked, a banner sits under the header on every page. Its action depends on context:

  • On a security pool page: Choose a branch… (links to that pool's Fork & recovery). Hidden once the branch choice is committed (12b, 13).
  • On the Universes page: no action (you're already there).
  • Elsewhere: Migrate REP… plus a “How to move shares and capital” link.

5. Watchlist (02–02f)

  • Open card: one field for a security pool address or shared link, one optional Question ID field, an Open button. The question-ID field searches only the user's saved security pools (02d: “Found in 2 of your saved security pools”). Both inputs are fixed single-line height; while checking, the spinner is inside the Open button, whose size doesn't change.
  • “View positions of another address” (closed disclosure): read-only mode for any address; the header then shows “Viewing as”.
  • Saved questions table: star, question title, security pool address, stage badge with the relevant date, your shares, Open. If the same question is saved in two pools, each row notes “Also saved in another security pool”. A row can link “REP staked in deposits not found on this device. Locate them” (→ 04d).
  • Saved security pools: star, address with collateral/policy/fees line, REP price status badge, capacity-in-use bar, your position (pledged REP, commitment, health, earned). Deploy a security pool… button.
  • Saved items that fail the entry check show “isn't a Statoblast security pool” (or question) with Remove. A question that is registered but not prepared in the current universe is never offered for removal (see Entry check).
  • Export / Import watchlist: the file also carries the deposits located on this device (schema).
  • Recently opened: last 20, a snapshot, not refreshed. Clear history.
  • Empty state (02c) explains the three ways in: paste a link or address, search a question ID in saved pools, or open something and star it.
  • Un-starring an item where you hold a position asks first (see 18).
  • Transactions save the touched question / security pool automatically.

6. Question pages (03–04e)

All question pages share a head: breadcrumbs, stage badge, “Binary · question ID {id}”, star + title, Open security pool button, a notice when the same question is also in another saved pool, and a stage stepper. Tabs: Shares, Reporting (with action badge), Inherited claims (only when present), Details. No right-hand column: the page uses the full width.

Stage stepper and the fork branch

  • Main path: Trading → Reporting opens/opened → Response window → Resolved, each with its date or a short consequence.
  • Fork is drawn as a branch, not as the next step: the main line ends at Resolved; a dashed curve leaves the line just before Resolved and drops to a separate “or Fork” step underneath (“Instead, if 2 outcomes reach 225 000 REP”). On phones (vertical stepper) the dashed curve goes around Resolved on the left and rejoins at “or Fork”.
  • At the fork step (04e) the stepper becomes Trading ended → Reporting opened → Ended undecided (danger-coloured dot) → Fork (current, “Waiting for a trigger”).
  • Inherited questions in a child universe before activation: badge “Paused until this branch is activated”, deadlines read “starts at activation” (design note on 03).

03 Shares

  • Fact strip (one row): Reporting opens (+ Add to calendar), Capacity free, REP price status, Holding fee, Purchase fee.
  • Your holdings: complete sets and each outcome's shares, each with what it pays. “Only one outcome wins.” and a closed “How shares work” disclosure.
  • Share actions: a segmented control with four launchers that always stay in place: Mint sets, Redeem sets, Migrate shares (after a fork only), Redeem winning shares (after resolution). Unavailable ones are disabled with the reason shown. 03b shows the other three forms.
  • Mint form (shared with the pool Questions drawer): collateral input with “max”, visual “2.50 WETH → 2.50 Yes + 2.50 No + 2.50 Invalid”, cost rows, before → after rows (your shares, wallet, capacity free), closed “Limits” disclosure (max fee, min sets), then Approve → Mint steps.

04 Reporting (game running)

  • Next-step banner states your situation and the one action: e.g. “You're behind on Yes · Add 420.01 REP to Yes before Jan 9, 14:00 UTC to take the lead · If Yes is still behind when the window ends, your 120.00 REP is lost.” with Add to calendar and a jump link. Other banner texts (no reports, tied, no REP staked, pending finalization) are in 04b.
  • REP staked per outcome card: per-outcome bars (others vs you), Leading/Behind badges with “N more to lead”; beside it the response window timeline (today, current end, end if you take the lead, latest possible end) and one line: “Only a report that raises the second-highest outcome extends the window.” Closed “How reporting works” disclosure.
  • Report an outcome: outcome radio list with stake per outcome, amount input with presets (Min, Take the lead, Full bonus share, Max), “Paid from your wallet · {balance}” (wallet only; no other funding source). Right side: “After this report” before → after rows (what you'd get back if the window ended now, your stake on the side, leader, window end) and the loss warning with the amount. Steps: Approve REP → Report.
  • Claim REP: your deposits with the claim button disabled until resolution; “Deposit #3 saved on this device”.
  • No fork control appears here. When the entered amount would bring a second outcome to 225 000 REP, the report's last step changes to a confirmation checkbox (“…Reporting then ends undecided and the universe can fork. This cannot be undone.”) and the button shows the amount; see the design note at the bottom of 04b.

04b Resolved: claim

  • Banner “Resolved as Yes · Claim 689.40 REP from your Yes deposits” and a pointer to redeem shares.
  • Table of your deposits with checkboxes for winning ones (preselected), deposited vs you receive; losing deposits show 0.00 and “Lost, no action needed” (listed only when saved on this device; never searched). One Claim {sum} REP button; its amount follows the checkboxes; all selected deposits are claimed in one transaction.

04c Inherited claims and Details

  • Shown in a child universe for a question that was in reporting when the parent forked. First read your REP in the frozen parent game; if zero, show “Nothing to claim” and read nothing more.
  • Otherwise the parent's deposit list is read once in full (needed for claims), with a progress bar “Preparing your claims · 120 of 400”, then kept on the device (the parent never changes).
  • Each winning deposit shows its payout before claiming; Claim one, or all in one transaction (“Claim 1 680.00 REP (2 deposits, 1 transaction)”). Losing deposits: “Lost: returns no REP; no action needed.” Disabled reasons: “Wait for the question to resolve.”, “Refresh to verify this claim.”, “Another claim transaction is pending.”
  • Details tab: question type, trading end, question ID, question contract (the QuestionLedger address; the only place it appears), security pool, minimum first report, response window, “Fork at 225 000 REP per outcome”, resolution rules, categories, tags.

04d Locate deposits

  • Shown only when the game's record of your REP on the winning side is larger than what this device knows (new device, another app, cleared storage). Can start while reporting is still open.
  • Split bar “Located 500.00 REP (1 deposit)” vs “Still searching 120.00 REP”; reassurance that unlocated REP is safe; search progress bar (“960 of 1 450”), time left, “Keep this tab open”.
  • “I know the deposit number” (closed by default): one read; errors “belongs to another address”, “There is no deposit #3 on Yes.”, “already claimed”.
  • Located deposits are claimable immediately; the remaining expected payout is shown. If the search ends without matching: “Couldn't find 120.00 REP of deposits. It is still safe.” + Search again.

04e Fork step

  • The only screen where a question offers the fork. Shown after two outcomes reach 225 000 REP: no more reports are accepted and reporting has ended undecided; triggering the fork is a separate transaction anyone can send.
  • Badge “Undecided · fork step”; tab badge “Fork”; outcome bars at the threshold.
  • “Fork the universe” card: danger notice “A fork cannot be undone. This universe freezes; everything moves to child universes Yes, No and Invalid.”; cost “Triggering costs you 12.40 REP, not returned. (REP supply grew since reporting started.)”; approval amount input (cost + 1 REP spare; the spender is the reporterLedger returned by getOwnForkAdmissionShortfall); steps Approve REP → Trigger universe fork (sub-line “Anyone can send this; needed once”).
  • With no shortfall the cost line, approval field and Approve step are hidden; Trigger is the only step. While loading, Trigger shows “Checking…”. After the fork, the fork banner and the pool's Fork tab take over.
  • Your own deposits in this state are read-only: “Your REP stays staked and carries to the child universes after the fork.” They are claimed there (04c).

7. Security pool pages (07–11, 06)

Shared head (portfolio-head.js): status badge, collateral and question policy, star + full address (copy, add a label), “Position of you {address}” selector (switch to any position owner, read-only), Refresh. Tabs: Overview, Capital, Questions (count), REP price (status badge), Liquidations (count), Fork & recovery (status). Tabs wrap; on phones a select replaces them. A forked pool shows a “Forked” badge.

07 Overview

  • Security pool capacity (in use / free bar, total pledged REP), REP price status with time left.
  • Your position gauge: health with marks for liquidation (85%), backing (100%) and your target (120%); below 900 px the mark labels become a legend line. Earnings with a link to Capital.
  • “Needs attention” items (e.g. reduction ready to release, claimable earnings) link to the section that acts.

08 Capital

  • Section nav (Deposit REP, Health target & commitment, Reduce commitment, Withdraw REP, Earnings) with each section's key value; on narrow screens it becomes a row above the content. A “Your position” summary column (pledged, commitment, health, target, withdrawable) sits beside the sections on wide screens and below on narrow ones.
  • Deposit REP: amount (wallet balance as unit hint) → Approve → Deposit. “Deposited REP backs nothing and earns nothing until you set a commitment.”
  • Health target & commitment: liquidation consequence always visible (“Below 85% health anyone can take over your commitment, and within an hour up to all your pledged REP goes to them as a liquidation penalty…”); inputs health target %, commitment (with Current / Max presets), optional extra REP; Preview before → after (target, REP needed, withdrawable, max commitment); steps only for what applies (Approve REP, Deposit REP and save target, Set commitment).
  • Reduce commitment: the queue is paid from free capacity in order, all-or-nothing, and can't be changed once queued. Show your commitment “10.00 → 6.00 WETH”, a bar of who's ahead of you vs your reduction, the free-capacity marker (“9.00 WETH free now, covers all 6.10”), and Release reduction (keep 6.00 WETH) when covered; otherwise disabled “Waiting for free capacity”; after a failed release “Retry release”.
  • Withdraw REP: amount with max withdrawable.
  • Earnings: WETH and REP vested, Claim; “More vests over 7 days.”

09 Questions (09b, 09c)

  • Your saved questions in this pool (“Showing the 3 you saved, of 14 registered here.”) — never the full registry. Find or register by question ID: input starting with 0x is hex, anything else is decimal.
  • 09c states: Registered here (open, mint); Not registered here (Register question; for an open pool); invalid input; not a question. Register is disabled with its reason when the question can't be registered: only Yes/No questions, trading not yet ended, universe not forked (SecurityPoolFactory.sol registration checks). A question registered here but not yet prepared in the current child universe shows “Registered, not prepared in this universe” and links to Fork & recovery. Invalidate the session entry-check cache after Register and after Prepare.
  • 09b fixed question list: “Which questions can be registered: Fixed question list” and the approved IDs; others can't be registered.
  • Mint drawer uses the shared mint form with a question picker and Find by ID.

10 REP price

  • Accepted REP price (REP per WETH, report #, deviation), the price used for health and for liquidation, validity countdown.
  • Report a price: shared component (price-report.js) with persistent steps: prepare, approve, report, settle, recover, return funds. Dispute window is 5 minutes. Return funds for older report IDs; send one token elsewhere (optional); recover a report that settled without a price.

11 Liquidations

  • Positions this device knows: your own, ones opened by ID (“Position ID → Open position”, reads accountOf(id) and liquidationStarted(id)), and ones from shared links. No scan over all position IDs: anyone can open positions, so a scan is unbounded.
  • Position #7: health 78%, started time, takeover reward growing over one hour (bar from ≥ 186.50 REP now to all 746.00 REP by 00:58), max takeover now / later. Take over with your limits (start empty; suggested “Most pledged REP you'll end with”) and before → after for your position. Cure: permissionless, no reward, owner keeps REP; disabled when pool capacity is too low.
  • Taker side says “takeover reward”; the owner side says “liquidation penalty”. Never “bonus”.

06 / 06b Deploy a security pool

  • Four sections with a live summary: collateral & universe, price reports (minimum stake, priority fee), questions (any question / fixed question list), economics (multiplier in %, fees, minimum commitment, vesting). Origin universe ID shown.
  • 06b: one button per transaction (deploy, then setup stages incl. “Anyone can send this; needed once” shared steps), progress saved on the device.

8. Fork and recovery (12, 12b, 13, 15)

  • 12 Branch choice: “branch” is defined once here as this security pool's copy in a child universe. Diagram of the parent and child universes; pick Yes / No / Invalid; deadline “Choose by Jan 18, 14:00 UTC”; consequence visible: if you don't choose, your pledged REP goes to claimants in every branch and your commitment ends. Commit choice requires an “irreversible” checkbox. Then seven persistent steps (prepare question, commit choice, start migration, branch REP price, repair auction, activate, open your position) each with a visible reason when locked. Recovery for share holders: question picker, claim recovery, transfer rights.
  • 12b Branch REP price (after choosing No): the shared price-report component for the branch; one recapitalization deadline Jan 25, 14:00 UTC for the branch price, the auction close and earliest activation. If no branch price is accepted the auction can't fill, bids are refunded, and the branch activates under-collateralized.
  • 13 Repair auction: lots and bid-price scale; the lowest REP-per-lot asks win and all winners get the highest winning ask; your bids with status (winning, outbid: “Lower asks already fill the auction”), refunds and auction vault controls.
  • 15 Universes & REP migration: current, parent and child universes with your REP in each; choose an outcome, amount, approve, migrate. Burning and migrating are irreversible (stated). Shares and REP can be migrated to more children later; there is no REP migration deadline.

9. Price reports and app-wide states (14, 17, 18)

  • 14 Price reports: latest report of each saved security pool (status dot, pool, REP price, status like “Dispute window · 3 min left”), Open report by ID, detail panel with the report stepper (Reported → Dispute window → Settle → Funds returned) and Settle (anyone can settle; shows the bounty).
  • 17 Transaction states: every transaction button goes through review → wallet → pending → confirmed in place; plus canceled, reverted (with reason), “Changed since you reviewed” (forces Review again), replaced. Disabled buttons always carry a visible reason.
  • 18 App states: no wallet, wrong network, loading (skeletons keep layout), empty, RPC error (data stays readable, retry), stale (“Updated 3h ago”), un-star confirmation for held positions.

10. Shared components and behaviours

Address display

  1. Show the full address (mono, no wrapping) when it fits its line.
  2. If it doesn't fit, move the address onto its own line (in a key/value list, the value goes below the key).
  3. Only if it still doesn't fit, shorten to 0x + first 10 … last 10 characters and add a copy button that copies the full value. Never shorten more than that (short forms are spoofable). Wrapping is a last resort only.

The mockup implements this in shell.js (fitAddresses); implement it as a component that measures its container (ResizeObserver).

Transaction steps

  • A step list shows only the steps that apply, numbered, each with a persistent button (it doesn't disappear when done; done steps show ✓ and a muted style). A locked step shows its reason visibly beside the title (e.g. “Approve REP first.”), and the same text is the button's accessible description.
  • Shared steps that anyone may send carry the sub-line “Anyone can send this; needed once”.
  • Wide containers: action column on the right; narrow: the button goes under the text.

Other patterns

  • Next-step banner: eyebrow (state), one-sentence instruction with amount and deadline, one consequence line, up to two actions.
  • Before → after rows list only values the action changes.
  • Fixed-size inputs: one-line inputs keep their height; long typed values are clipped with an ellipsis; units/hints sit inside the input on the right.
  • Tables stack into label/value cards whenever their container is narrower than about 1000 px (container query), not just on phones.
  • Layout widths: test 1440, 1280, 1024, 900, 768, 390, 360. Below 1100 px side columns move below the main column; below 640 px the bottom bar and select-style tabs apply.
  • Dates: “Jan 9, 14:00 UTC”; relative “in 2d 13h” only next to an absolute date. Durations “7 days”. Gas prices in nanoETH/gas (the repository unit rule, enforced by bun run check:unit-terminology).
  • Light and dark themes.

11. Data loading (no event logs)

The full plan with per-row read counts, the request budget and the abuse analysis is 19 Refresh plan. Summary:

  • Refresh rules: the open page every new block in one block-pinned multicall; saved items every block up to 25 (beyond that 10 rotate per block); recently opened never refreshed; hidden tab paused. Staleness: any row whose data is more than 3 minutes behind the chain head shows “Updated {time} ago” and its transaction buttons are paused with “Refresh to continue.” (18); within 3 minutes no age is shown.
  • Entry check before anything joins a read batch: security pool via isSecurityPool(address) on the factory; a question via getQuestionLedger(questionId, universeId) on that security pool, read with allowFailure. It has three outcomes: a ledger address (registered and prepared); revert “Question not registered” (not registered here, “Not a Statoblast question”, offered for removal); revert “Question pool unavailable” (registered but not prepared in this universe, e.g. a child universe before “prepare question”: keep the item and link to Fork & recovery). The check runs in the first multicall, reads in the second; results are cached per session and invalidated after Register and Prepare.
  • Universe scope: a question is really (security pool, question ID, universe). Routes keep the existing universe / network / simulation query context (as buildQuestionPoolHref in SS/lib/routing.ts does today), so a shared link opens the same universe. Saved items are stored per network as (security pool, question ID) and shown with their state in the currently selected universe; where that universe has no ledger yet, the row shows “Not prepared in this universe”.
  • Device storage and export: reuse localEntityStore.ts (app “statoblast”, kinds “question” and “pool”, per network, limit 500) and FavoriteToggle.tsx (aria-pressed; label “Saved: {name} in security pool {address}”). Also stored per network: history (last 20), located deposits {game, outcome, depositor, index}, search cursors {game, outcome, depositor, nextIndex, block}, and deploy progress. Export file: {"version": 1, "chainId", "saved": [{kind, pool, questionId?, label?}], "deposits": [{game, outcome, depositor, index}]}. Import treats every entry as untrusted: validate the shape and chainId, run the entry check on saved items, and verify each deposit with one getDepositsByOutcome(outcome, index, 1) read (depositor must match); merge by key, never overwrite. Errors: “Not a Statoblast watchlist file.”, “This file is for another network.”, and a count of skipped entries.
  • Your deposits:
    • Total per side with no search: getLocalUnresolvedPrincipalByVaultAndOutcome(wallet, outcome) × 3, where wallet is the depositing wallet address. All zero → nothing to locate.
    • Saved at deposit time: after the report confirms, read getDepositsByOutcomeLength at the receipt block and its parent block; the entries between are that block's deposits (getDepositsByOutcome); those whose depositor is you are yours. Saved per chain, game, outcome and depositor. The first report of a game deploys the game in the same transaction, so a game with no code at the parent block counts as length 0. Both reads are of very recent state (the receipt's block and its parent), which ordinary nodes serve; if the parent-block read fails, fall back to the search below. See open question on decoding the receipt instead.
    • Carried to another device by Watchlist export/import.
    • Search only when totals differ: page getDepositsByOutcome(outcome, start, 30), 2 pages per refresh, cursor saved, stop when located deposits add up to your total; only for the open question; cursors advance only to a block a few behind head (reorg safety). Losing sides read 0 after settlement and are never searched.
    • Claiming uses withdrawFromEscalationGame(outcome, depositIndexes[]) with all selected indexes in one transaction. It is permissionless but needs one depositor per call, and after a fork it reverts (“Deposits carry to child games”): deposits then carry to the child games (04c).
  • Inherited claims: read your REP in the frozen parent first; zero → stop. Otherwise read the parent list once in full (proofs need every entry) and keep it; check each of your claims individually each refresh.
  • Remove today's global loaders: the question list that reads every registered ledger, the deposit pager over every deposit, and the per-block reload with 19 bytecode checks (cache verified modules per session). Measured today ≈ 130 requests per block on a security pool page; target ≈ 3–5.

12. Wording rules and glossary

One name per concept. Product text never uses internal names (Zoltar, ledger, proofs, cohort, callback, admission policy).

Concept Use Don't use

Getting REP back from deposits Claim (“Claim N REP”); losing deposits need no action settle, clear, recover
Getting collateral for shares Redeem settle, claim
Price-report finalization Settle —
Universes after a fork child universe; on 12/12b/13 branch = this security pool's copy in a child universe child (alone)
Child universe not created “Not created yet” / “Created” not deployed
The pool contract security pool portfolio, vault (except auction vault)
REP price “REP price”, unit “REP per WETH”; header chip “1 REP = 0.0045 ETH” price (alone), REP/WETH
Fees “Holding fee 10%/yr”, “Purchase fee 1% (min 0.001 WETH)”; mint form “Fee” charge, premium
Capacity in use, free, max commitment healthy capacity, settlement demand
Health Health %, Health target, Liquidation price, badge “Below liquidation” conservative health, boundary
REP backing a commitment Pledged REP principal, committed REP
A provider's stake in a pool position account, vault
Retirement Reduce commitment; state “In queue” retirement, cohort
Liquidation incentive taker “takeover reward”; owner “liquidation penalty” bonus

Rules: “·” only joins same-kind metadata; show only rows and steps that apply; when a consequence is unknown, don't invent it.

13. Verified contract facts

Checked against the contracts; the mockups depend on them. Numbers in the mockups such as 225 000 REP, 85%, 5 minutes and 7 days are example values: read them from the contracts, never hard-code them in copy (see the table below).

Example value Read from
225 000 REP per outcome (fork / non-decision threshold) Per game: EscalationGame.nonDecisionThresholdAttoRep, set from Zoltar.getNonDecisionThresholdAttoRep(universeId); it depends on REP supply.
1.00 REP minimum first report Per game: EscalationGame.startBondAttoRep.
5-minute price-report dispute window The price feed's immutable settlementTime (SharedPoolPriceFeed.sol).
Earnings vest over 7 days A security pool deploy parameter (06 “Reward vesting”); read it from the pool.
Liquidation below 85% health; 120% target From the pool's security multiplier and price feed (liquidation price) and the position's saved target; never a constant in copy.
Takeover reward reaches all pledged REP after 1 hour LIQUIDATION_AUCTION_DURATION (SecurityPoolCommitmentIndex.sol).
  • Reports are paid from wallet REP only.
  • Losing deposits return nothing and need no action.
  • Inherited winning deposits can be claimed together in one transaction; payouts are known before claiming.
  • Attrition begins 3 days after the reporting game starts; the cost to keep a side alive then rises over up to 7 weeks; once it passes the second-highest side, reporting closes and the leader wins (EscalationGame.sol, EscalationGameCalculations.sol, Constants.sol).
  • Only a report that raises the second-highest outcome extends the window.
  • “Full bonus share” fills your side to min(1.5 × largest other side, threshold): winners split 60% of the second-highest side; 40% is burned.
  • Deposits are capped at the per-outcome threshold. When two outcomes reach it, the game is in its non-decision state and accepts no deposits; the fork is a separate, permissionless trigger (QuestionForker.forkZoltarWithOwnEscalationGame) that pulls any REP shortfall from the caller; the shortfall and the spender to approve (reporterLedger) come from QuestionForker.getOwnForkAdmissionShortfall. In the non-decision state deposits can't be withdrawn (“Non-decision done”); after the fork they carry to the child games.
  • Resolution: if no outcome has any REP, the question resolves Invalid; a tie doesn't resolve: the question stays unresolved until one outcome strictly leads (EscalationGameProofVerifier.resolveQuestion).
  • Only Yes/No questions can be registered in a security pool, before trading ends and while the universe hasn't forked (SecurityPoolFactory.sol).
  • Missing the branch choice: pledged REP goes to claimants in every branch; the commitment ends.
  • No accepted branch REP price: the repair auction can't fill, bids are refunded, the branch activates under-collateralized.
  • Repair auction: lowest REP-per-lot asks win; all winners get the highest winning ask.
  • Shares and REP can be migrated to more child universes later; no REP migration deadline.
  • Reduce-commitment queue: can't be changed once queued, all-or-nothing, served when free capacity covers it. Cure is permissionless, pays no reward, and the owner keeps their REP.
