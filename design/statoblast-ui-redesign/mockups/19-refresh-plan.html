Data plan · for design and engineering review · no contract changes

What is read, and when

Nothing is listed globally. You reach a question or security pool by link or address, or a question by ID inside its security pool; starring keeps it on the Watchlist. Reads happen when you open a page, press Refresh, or after your own transaction; auto-refresh is opt-in. Everything else is read only while you look at it.

Saved items, history and the last data read are saved per app and network on this device (store limit 500). On a slow RPC the page shows the saved data at once with its age, and fills in sections as reads arrive; a read that times out keeps the old value and shows “Couldn't refresh, showing data from {age} ago.”

Decided trade-off · no browsing

No screen lists questions or security pools that anyone can create, including a security pool's registered questions. There is no Questions tab: a question exists only inside a security pool, with its own shares and reporting there, so every question is reached as (security pool, question ID) through a link, the Trading app, the Watchlist, or lookup by ID inside one security pool. Whatever people save is read when they open the Watchlist or press Refresh. Spam can't reach the screen, at the cost of not browsing what a security pool backs.

Product decision

Entry check

Every ID, address, link, saved and history entry is checked before it joins a read batch, without calling the address itself. One hostile target would otherwise fail the whole multicall.

Security pool
isSecurityPool(address) on the factory (SecurityPoolFactory.sol:62)
Question link
Names a security pool and a question ID: the security pool passes the check above, then getQuestionLedger(questionId, universeId) on it (SecurityPool.sol:231) finds the question. Question ledger addresses are never typed; they appear only in a question's “Resolution rules and details” disclosure
Question ID
Never searched app-wide: the same question can sit in any number of security pools. Inside one security pool (Find by question ID): one getQuestionLedger(questionId, universeId) read, “Not registered here” otherwise. Anything else needs a link or a security pool address; the Watchlist has no question-ID search
Fails
Not a security pool, or “Question not registered”: “Not a Statoblast question / security pool”, never read, offered for removal. “Question pool unavailable”: registered but not prepared in this universe; kept, linked to Fork & recovery, never offered for removal. Cache cleared after Register and Prepare.
Order
The check runs in the first multicall and the target's reads in the second; results are cached for the session, so the ceiling holds on first open
Bytecode
Factory-registered contracts are canonical code (:179), so saved items and history skip bytecode checks; the open page verifies fully, at most one security pool per refresh, cached per session

Locating your deposits · contract state only

The app never reads event logs. Claiming needs each deposit's position (withdrawFromEscalationGame(outcome, depositIndexes[])); everything else comes from single reads.

No logs
  1. Per wallet: deposits are made from your wallet. Totals, saved positions, searches and claims are per wallet address.
  2. Your total per side, no search: getLocalUnresolvedPrincipalByVaultAndOutcome(you, outcome) ×3. All zero → nothing to locate. Shown on Reporting while the game runs. Retired (losing) sides read 0 after settlement, so losing deposits are shown only when saved and are never searched; they return no REP and need no action.
  3. Saved when you deposit: after the transaction confirms, read getDepositsByOutcomeLength at the receipt's block and at its parent block. The entries between them are exactly that block's deposits (getDepositsByOutcome); every one whose depositor is you is yours. Saved per chain, question, outcome and depositor (about 3 reads, once). The first report deploys the game in the same transaction: no code at the parent block counts as length 0. If the parent-block read fails, fall back to the search below.
  4. Carried by Watchlist export/import to another device.
  5. Search only when totals differ (new device, another app, cleared storage): page getDepositsByOutcome(outcome, start, 30), as a foreground job: it runs on its own loop while the screen is open, whether or not Auto-refresh is on, one request in flight, 2 pages per request, pausable, cursor saved, backing off on timeout; it stops the moment located deposits add up to your total. Only for the open question; may start while the game runs. A deposit number can be entered and checked with one read; reaching the end unmatched shows “Search again”. Screen 04d.
  6. Inherited claims: read your REP in the frozen parent game first; zero → nothing more. Otherwise proofs need every parent entry, so the parent list is read in full once and kept (04c).
  7. Located deposits are re-read each refresh; amounts drop to 0 once claimed. Cursors advance only to a block a few behind head, so a reorg can't skip a deposit.

If someone tries to overload it

Attack Effect
Deploy thousands of questions or security pools None: nothing is listed globally
Register spam into an open security pool None: only saved items and lookup by ID
Share a link to a fake question Rejected by the entry check before any read
Flood a starred game with deposits Each deposit is at least the start bond and a side caps at the threshold; only matters for a search on a new device: a longer search job, never more per request; saved positions need no search
You star many items Your own choice: Refresh on the Watchlist reads them in chunks of 25 (“Refreshing… 2 of 4”)
